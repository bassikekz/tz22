# Доменная модель и правила прикладных модулей ядра

Документ описывает сущности, состояния и инварианты прикладных модулей ядра
платформы CA PS в объёме общего ТЗ П.22 v.2. Состав модулей и границы развёртывания
приняты решением по архитектуре (`docs/03-arhitektura-i-razvertyvanie.md`): ядро —
модульный монолит, рассылка, публичный контур и коннекторы — отдельные сервисы.

Охват: **M1** Каталог обучения (7.1, 7.2), **M2** Назначения и прохождение (7.3),
**M3** Тестирование (7.4), **M4** Кампании и governance (7.5, 7.16, 7.17),
**M7** Оценка и показатели (7.10, 7.11, 7.13, 7.19), **M8** Группы риска и
адаптивное обучение (7.9, 7.12, 7.18), **M9** Пересмотр результатов (7.20).

Обозначения: номер раздела общего ТЗ указан в скобках после каждого правила.
Пометка **«определяется методикой (раздел 17)»** означает, что ТЗ требует наличие
механизма, но конкретные значения, формулы, пороги или перечни закрепляются отчётом
предпроектного обследования и согласованными методиками (раздел 17).

## 2. Состояния и переходы

### 2.1 Версия учебного материала (7.2; мес. ТЗ 3.1)

| Из | В | Инициатор | Что проверяется |
|---|---|---|---|
| — | черновик | уполномоченный оператор с правом добавления | наличие наименования, владельца, версии, содержимого (мес. ТЗ 3.1) |
| черновик | черновик (изменение) | владелец либо оператор с правом изменения | право на изменение проверяется приложением (10; мес. ТЗ 4) |
| черновик | опубликована | оператор с правом публикации | полнота реквизитов, право на публикацию, статус актуальности материала (7.2; мес. ТЗ 3.1) |
| опубликована | опубликована (повторное открытие) | оператор | опубликованная версия доступна для повторного открытия и неизменяема (мес. ТЗ 3.1) |
| опубликована | не актуальна | владелец материала | ведение статуса актуальности; ранее зафиксированные прохождения сохраняются (7.2) |

Правила: **черновик участнику не выдаётся ни в каком виде** — ни как назначение, ни
как содержимое (мес. ТЗ 3.1, 3.2); для назначения доступна только опубликованная
версия (7.2; мес. ТЗ 3.1). Изменение содержимого опубликованной версии выполняется
созданием новой версии; подмена содержимого в опубликованной версии запрещена (7.2, 10).

### 2.2 Учебная программа (7.1)

Состояния: черновик → действует → не актуальна (по сроку актуальности) → удалена.
Переходы инициирует владелец программы либо оператор с соответствующим правом;
регистрация, изменение и удаление программ журналируются (9). Состав состояний сверх
перечисленных определяется методикой (раздел 17): ТЗ требует только «управление
жизненным циклом учебных программ» (7.1).

### 2.3 Назначение (7.3)

| Из | В | Инициатор | Что проверяется |
|---|---|---|---|
| — | создано | оператор, правило периодического обучения, правило корректирующего назначения | участник в области назначения, версия материала опубликована (7.2, 7.3) |
| создано | доступно участнику | платформа | доступность не позднее 5 минут после публикации при штатной работе интеграций (7.3; мес. ТЗ 3.2) |
| доступно | в процессе | участник | участник входит в число назначенных (мес. ТЗ 3.2) |
| в процессе | выполнено | участник | полнота результата; неполный результат не обозначается как успешный (мес. ТЗ 3.2) |
| доступно / в процессе | просрочено | платформа по контролю сроков | истёк срок обязательного ознакомления либо срок прохождения (7.2, 7.3) |
| любое незавершённое | отменено | оператор; применение исключения | основание отмены, область и срок действия исключения (7.17) |

### 2.4 Прохождение (7.3; мес. ТЗ 3.2)

Состояния: не начато → начато → завершено. Запись фиксирует идентификатор материала,
версию, участника и время (мес. ТЗ 3.2). Статус отображается участнику и
уполномоченному оператору; другие участники персональные результаты не видят
(мес. ТЗ 3.2, 4). Завершённая запись неизменяема; корректировка выполняется только
через пересмотр результата (7.20).

### 2.5 Попытка тестирования (7.4)

Состояния: назначена → выполняется → проверена (автоматическая проверка) →
оценена (итоговая оценка) → зачтена либо не зачтена. При неудовлетворительном
результате назначается повторное тестирование (7.4). Порог удовлетворительного
результата и количество допустимых попыток определяются методикой (раздел 17).
Состав и порядок вопросов фиксируются в попытке — иначе рандомизация (7.4) делает
результат непроверяемым.

### 2.6 Кампания (7.16)

| Из | В | Инициатор | Что проверяется перед переходом |
|---|---|---|---|
| — | черновик | ответственный за кампанию | — |
| черновик | на согласовании | ответственный | заполнены цель, аудитория, период, сценарий, канал, допустимые действия, уровень сложности, exclusion list, контрольная группа (где применимо), ответственный (7.16) |
| на согласовании | утверждена | согласующий (роль согласования) | согласование оформлено и зафиксировано; сценарий утверждён (7.16, 7.5) |
| на согласовании | черновик | согласующий (возврат) | замечания зафиксированы |
| утверждена | запланирована | ответственный | период и расписание заданы; рандомизация времени отправки настроена, где применимо (7.5) |
| запланирована | выполняется | платформа по расписанию; оператор | канал согласован, отправители контролируемы, учебные домены и landing pages согласованы (7.6); exclusion list применён (7.17); контрольная группа исключена из воздействия (7.5) |
| выполняется | приостановлена | оператор | основание приостановки журналируется (9) |
| приостановлена | выполняется | оператор | условия запуска подтверждены повторно |
| выполняется / приостановлена | завершена | платформа по окончании периода; оператор | события участников собраны, статистика сформирована (7.6) |
| любое до запуска; выполняется; приостановлена | отменена | ответственный либо согласующий | основание отмены журналируется (9) |

Правила: запуск кампании без полного состава параметров раздела 7.16 не допускается;
моделируемая атака выполняется только в рамках утверждённого сценария и не приводит
к фактической компрометации (7.5, 10.1). Запуск и остановка кампаний журналируются (9).
Кампания по инициативе AI-SecOps запускается в рамках заранее утверждённого сценария
либо после подтверждения уполномоченного оператора (7.9, 8.1).

### 2.7 Пересмотр результата (7.20)

| Из | В | Инициатор | Что проверяется |
|---|---|---|---|
| — | зарегистрировано | участник (обращение/возражение) либо оператор | указан результат-объект и содержание обращения (7.20) |
| зарегистрировано | на рассмотрении | ответственный работник | полномочия ответственного (10) |
| на рассмотрении | результат изменён | ответственный | зафиксировано основание изменения; новый статус результата (7.20) |
| на рассмотрении | результат подтверждён | ответственный | основание решения зафиксировано (7.20) |
| результат изменён | исключён из risk scoring | платформа по решению | признак исключения и основание сохранены; показатели пересчитаны (7.20, 7.11) |

История пересмотра ведётся полностью; действия ответственных работников
журналируются (7.20, 9). Исходная запись результата не удаляется — изменяется её
статус (7.20, 10 «защита от несанкционированного удаления данных»).

## 3. Инварианты и правила

| № | Правило | Раздел ТЗ |
|---|---|---|
| И-01 | Опубликованная версия материала доступна для назначения; черновик участнику не выдаётся | 7.2; мес. ТЗ 3.1 |
| И-02 | Неназначенный участник не получает ни назначение, ни результаты других участников | мес. ТЗ 3.2, 4 |
| И-03 | Назначенное обучение доступно работнику не позднее 5 минут после публикации при штатной работе интеграций | 7.3; мес. ТЗ 3.2 |
| И-04 | Неполный результат не обозначается как успешный | мес. ТЗ 3.2 |
| И-05 | Единичная ошибка работника не приводит автоматически к максимальному уровню риска без учёта иных факторов и истории | 7.11 |
| И-06 | Методика оценки учитывает положительное поведение, включая корректное сообщение о подозрительном сообщении | 7.10 |
| И-07 | Методики формирования рейтингов и risk scoring документированы и воспроизводимы: тот же вход и та же версия правила дают тот же результат | 7.13; 17 |
| И-08 | Ошибочный результат исключается из risk scoring с обязательной фиксацией основания и истории пересмотра | 7.20 |
| И-09 | Реальные пароли, MFA-коды, PIN, токены, банковские реквизиты не сохраняются: фиксируется только факт действия, значение немедленно отбрасывается либо необратимо обезличивается и не попадает в журналы, отчёты и интерфейс | 7.6, 7.7, 10.1 |
| И-10 | Моделируемая атака проводится в рамках утверждённого сценария, без реального вредоносного ПО и без фактической компрометации | 7.5, 7.8, 10.1 |
| И-11 | Полномочия проверяются на стороне приложения, а не только в интерфейсе; доступ к персональным результатам и рейтингам разграничивается | 7.13, 10; мес. ТЗ 4 |
| И-12 | Автоматическое назначение обучения и тестирования по сведениям AI-SecOps допускается только в рамках заранее утверждённых правил | 7.9, 8.1 |
| И-13 | Exclusion list применяется до запуска кампании; для исключения хранятся основание, владелец, срок, область действия и история изменений | 7.17 |
| И-14 | Контрольная группа, где применимо, не получает воздействия кампании и учитывается при анализе результатов | 7.5, 7.16 |
| И-15 | Каждое прикладное действие попадает в журнал (пользователь, время, объект, операция, результат); секреты в журнал не пишутся | 9; мес. ТЗ 4 |
| И-16 | Записи прохождения, попыток и событий участника неизменяемы; корректировка — только через пересмотр результата (7.20) | 7.20, 10 |
| И-17 | Аудиозапись голосового взаимодействия создаётся только при наличии предусмотренных Заказчиком оснований и отдельного согласования | 7.7 |
| И-18 | Для управленческой и общей аналитики используются агрегированные показатели подразделений, филиалов и групп риска | 7.13 |

## 4. Модель расчёта показателей

### 4.1 Входные факторы

| Показатель | Входные факторы | Раздел ТЗ |
|---|---|---|
| Показатель осведомлённости (awareness score) | результаты обучения, результаты тестирования, результаты киберучений, результаты моделируемых атак, положительное поведение (включая корректное сообщение о фишинге) | 7.10 |
| Показатель устойчивости | результаты обучения, результаты тестирования, результаты фишинговых кампаний, повторяемость ошибок, результаты голосовых проверок, результаты проверок через средства обмена сообщениями, факт и скорость сообщения о подозрительной активности, результаты корректирующего обучения, иные утверждённые Заказчиком факторы, сведения AI-SecOps | 7.11, 8.1 |

Веса факторов, шкалы уровней и пороги отнесения к повышенному риску **определяются
методикой (раздел 17)** — ТЗ закрепляет только состав учитываемых факторов и
ограничение И-05 (7.11).

### 4.2 Состав baseline (7.19)

| Показатель baseline | Источник данных | Модуль |
|---|---|---|
| knowledge score | попытки тестирования, итоговые оценки | M3 → M7 |
| доля успешного прохождения тестирования | попытки тестирования | M3 → M7 |
| click rate | события участника «переход по ссылке» | M4 → M7 |
| доля попыток ввода учётных данных | события участника «попытка ввода учётных данных» (только факт, без значения — И-09) | M4 → M7 |
| attachment interaction rate | события «открытие учебного вложения» | M4 → M7 |
| reporting rate | события «сообщение о фишинге» | M4 → M7 |
| time-to-report | время от получения сообщения до сообщения о нём работником | M4 → M7 |
| repeat-failure rate | повторяемость ошибок по истории событий и результатов | M7 |
| completion rate | назначения и прохождения | M2 → M7 |

Показатели baseline формируются на первоначальном этапе внедрения и используются
для оценки динамики (7.19). Целевые показатели улучшения в ТЗ не заданы: они
определяются после получения исходных данных и закрепляются Программой и методикой
испытаний либо согласованными эксплуатационными документами (7.19).

### 4.3 Версионирование правил расчёта и пересчёт истории

- Каждый рассчитанный показатель, рейтинг и baseline хранит ссылку на версию правила
  расчёта и период её действия — без этого требование воспроизводимости не выполняется (7.13).
- Изменение методики создаёт новую версию правила; ранее рассчитанные значения
  сохраняются вместе со своей версией, чтобы анализ динамики не искажался (7.10, 7.13).
- Пересчёт истории по новой версии правила выполняется как отдельный результат с
  явным указанием версии; замещение ранее опубликованных значений без сохранения
  прежних не допускается (7.13 — воспроизводимость; 10 — защита от удаления данных).
- Пересчёт обязателен после исключения ошибочного результата из risk scoring (7.20).
- Глубина хранения истории и регламент пересчёта определяются методикой (раздел 17)
  и требованиями retention (10.2, 17).

### 4.4 Разграничение персональных и агрегированных показателей (7.13)

| Вид показателя | Доступ | Раздел ТЗ |
|---|---|---|
| Персональный показатель, персональный рейтинг, персональный результат | только пользователям с соответствующими полномочиями; сам участник видит свои результаты | 7.13, 10; мес. ТЗ 4 |
| Агрегированные показатели подразделений, филиалов, групп риска | управленческая и общая аналитика — предпочтительный режим | 7.13 |
| Передача в AI-SecOps и SIEM | в объёме раздела 8.1, с журналированием всех действий | 8.1, 9 |

Минимальный размер агрегата, при котором агрегированный показатель не раскрывает
персональный результат, **определяется методикой (раздел 17)** и требованиями privacy (10.2).

## 5. Адаптивное обучение и группы риска

### 5.1 Назначение по типу ошибки (7.18)

| Выявленный тип ошибки (источник) | Допустимые мероприятия по ТЗ |
|---|---|
| Переход по ссылке в учебном фишинге (событие участника) | учебный материал по теме, короткий корректирующий курс, повторная проверка |
| Попытка ввода учётных данных (только факт, И-09) | учебный материал, короткий корректирующий курс, повторное тестирование, повторная проверка |
| Открытие учебного вложения | учебный материал, короткий корректирующий курс, повторная проверка |
| Отсутствие сообщения о подозрительном сообщении | учебный материал, повторная проверка |
| Неудовлетворительный результат тестирования | повторное тестирование (7.4), короткий корректирующий курс |
| Повторяемость ошибок (repeat-failure) | дополнительное обучение, повторное тестирование, повторная проверка; включение в группу риска (7.12) |
| Ошибка в голосовой проверке либо проверке через мессенджер | учебный материал по каналу, короткий корректирующий курс, повторная проверка |

ТЗ перечисляет типы мероприятий (7.18) и не задаёт соответствие «тип ошибки →
конкретный материал»: это соответствие **определяется методикой (раздел 17)**
(модель адаптивного обучения) и закрепляется как утверждённое правило автоматического
назначения. Обязательна оценка изменения результата после обучения (7.18) и контроль
выполнения корректирующих мероприятий (7.9, 7.12).

### 5.2 Ограничения автоматизации

- Автоматическое назначение дополнительного обучения и повторного тестирования
  выполняется **только в рамках заранее утверждённых правил** (7.9, 8.1).
- Автоматическое формирование перечней работников для дополнительного обучения и
  повторного тестирования допускается; предложения по дополнительным проверкам
  устойчивости формируются как предложения, а не как запуск (7.9).
- Запуск массовых, целевых фишинговых, голосовых и messenger-кампаний по инициативе
  AI-SecOps — в рамках заранее утверждённого сценария **либо после подтверждения
  уполномоченного оператора** (7.9, 8.1).
- Сведения, полученные от AI-SecOps, используются в рамках утверждённой методики
  формирования групп риска (7.12); отнесение к группе риска по единичному сигналу
  без учёта истории запрещено (И-05, 7.11).
- Все действия по автоматическому назначению и запуску журналируются (8.1, 9).
