# Постановки для разработки: ядро результатов 1 и 2 (CA_PS-2026-10)

Задачи Senior-разработчика П.22 октябрьского объёма: P22-66, P22-67, P22-68, P22-70, P22-74. Источники: `docs/source/tz-ca_ps-2026-10.txt`; `docs/arch/02-domennaya-model.md` (сущности, состояния, инварианты И-01…И-16); `docs/arch/01-moduli-i-granicy.md` (модули M1, M2, M11, M12, события, внешний API); `docs/arch/04-bezopasnost-i-privacy.md` (роли, матрица прав, аудит); `docs/05-otkrytye-voprosy.md` (реестр вопросов). Общее для всех разделов: ядро — модульный монолит `core`; изменяющие запросы несут `Idempotency-Key`; прикладные операции доступны только после аутентификации (мес. ТЗ п. 4); журнал ведёт M12 (P22-76) по вызову из прикладного модуля, состав записи — пользователь, время, объект, операция, результат. Значения, которых нет в ТЗ (форматы, лимиты, TTL, пороги), помечены как уточняемые с номером вопроса реестра.

## P22-66 — Результат 1: схема данных учебного материала — наименование, владелец, версия, состояние

**Основание:** ТЗ CA_PS-2026-10, пп. 3.1 и 7 (схема данных входит в состав результата) (+ общее ТЗ, раздел 7.2)
**Модуль:** M1 · **Компонент:** core

### 1. Что реализовать
1. Таблицу `material` (идентификатор, наименование, владелец, ссылка на текущую опубликованную версию, автор и время создания) и таблицу `material_version` (номер версии, состояние `draft`/`published`, реквизиты содержимого, автор, время создания и публикации).
2. Ограничения целостности: `UNIQUE (material_id, version_no)` — монотонная нумерация в пределах материала; `CHECK (state IN ('draft','published'))`; обязательность `published_at`/`published_by` при `state='published'`; `NOT NULL` по реквизитам раздела 2; запрет изменения опубликованной версии (правило БД + проверка в репозитории M1) — изменение содержимого выполняется только созданием новой версии.
3. Выдачу версий в области видимости участника запросом или представлением, куда `draft` не попадает по определению (И-01), контракт M1 → M2 «версии, допустимые для назначения» (только `published`), а также идемпотентные миграции прямого и обратного хода с фиксацией версии схемы и выписку DDL для передачи Заказчику (п. 7) — без полей для паролей, PIN, MFA-кодов и токенов (И-09).

### 2. Данные
Сущности «Учебный материал» и «Версия учебного материала» (`docs/arch/02-domennaya-model.md`, п. 1); категорирование, статус актуальности и сроки обязательного ознакомления в октябре не создаются (расширение — там же, п. 6). Создаются поля:

| Поле | Тип | Обязательность | Правило заполнения | Источник |
|---|---|---|---|---|
| `material.id`, `created_at`, `created_by` | uuid (PK), timestamptz, uuid | да | генерируется платформой; время сервера UTC; субъект сессии | платформа, M11 |
| `material.name` | text | да | непустое после обрезки пробелов; предельная длина уточняется (вопрос 7.3 реестра) | ввод оператора |
| `material.owner_principal_id` | uuid → `principal` | да | субъект с правом `material.add`; по умолчанию автор черновика | M11 (P22-74) |
| `material.current_published_version_id` | uuid → `material_version` | нет | заполняется при публикации, иначе `NULL` | P22-68 |
| `material_version.id`, `material_id` | uuid (PK), uuid (FK) | да | генерируется платформой; ссылка на материал | платформа |
| `material_version.version_no` | integer | да | 1 для первой версии, далее `max+1`; уникален в пределах материала | платформа |
| `material_version.state` | enum (`draft`,`published`) | да | при создании всегда `draft`; переход только `draft → published` | платформа |
| `material_version.content_ref` | text | да | ключ объекта в хранилище M16, равен `material_version.id` | M16 |
| `material_version.content_mime`, `content_size`, `content_checksum` | text, bigint, text | да | тип из перечня допустимых, фактический размер, контрольная сумма содержимого; перечень MIME и предельный размер уточняются (вопрос 7.3 реестра) | ввод оператора, M16 |
| `material_version.author_principal_id`, `created_at`, `updated_at` | uuid, timestamptz, timestamptz | да | автор черновика; время сервера UTC; `updated_at` не меняется после публикации | M11, платформа |
| `material_version.published_at`, `published_by` | timestamptz, uuid | обязательны при `state='published'` | заполняются однократно при публикации | P22-68 |

### 3. Интерфейс (API)
Собственных HTTP-эндпоинтов задача не вводит (API добавления — P22-67, публикации — P22-68); реализуется внутренний контракт M1:

| Метод и путь | Назначение | Кто вызывает | Требуемое право | Коды ответов, включая отказ в доступе |
|---|---|---|---|---|
| внутр. `M1.createDraft(material, version)` | создание материала и черновика версии | обработчик P22-67 | `material.add` | ок / `VALIDATION_FAILED` (422) / `FORBIDDEN` (403) / `UNAUTHENTICATED` (401) |
| внутр. `M1.getVersion(id, scope)` | чтение версии с учётом области видимости | M1, M2 | `material.read` (оператор), `material.read_assigned` (участник) | ок / `NOT_FOUND` (404) для `draft` в области участника / 403 / 401 |
| внутр. `M1.listAssignableVersions(material_id)` | версии, допустимые для назначения | M2 (P22-70) | `material.read` | ок — возвращаются только `published` (И-01) |
| внутр. `M1.markPublished(version_id, principal)` | перевод в `published` | обработчик P22-68 | `material.publish` | ок / `ALREADY_PUBLISHED` (409) / 403 / 401 |

### 4. Правила и инварианты
1. Версия хранит наименование (через материал), владельца, номер версии, состояние, содержимое и реквизиты — мес. ТЗ п. 3.1.
2. Опубликованная версия неизменяема; изменение выполняется созданием новой версии — И-01, общее ТЗ 7.2, 10.
3. Черновик недоступен в области видимости участника на уровне запроса, а не только интерфейса — И-01, И-11, мес. ТЗ пп. 3.1, 4.
4. Номер версии монотонен в пределах материала; назначение ссылается на конкретную `material_version_id` — `docs/arch/01-moduli-i-granicy.md`, п. 6.2.
5. Схема не содержит полей для паролей, MFA-кодов, PIN и токенов (И-09); данные отделены от приложения — перезапуск и восстановление из копии не приводят к потере записей — мес. ТЗ п. 4, проверка 5 п. 8.

### 5. Журналирование
Записываются: `schema.migrate` (объект — версия схемы), `material.create`, `material_version.create`, отказы по ограничениям целостности (с кодом ограничения). Атрибуты: пользователь либо техническая учётная запись, время, объект (`material_id`, `material_version_id`), операция, результат «успех»/«отказ» с причиной. Не пишутся: содержимое материала, значения любых секретов, параметры подключения к БД (мес. ТЗ п. 4, И-09).

### 6. Зависимости и блокировки
- Предшественники: P22-63 (согласование контрольных данных и форматов), P22-64 (стенд). Потребители: P22-67, P22-68, P22-70.
- Вопросы реестра: **7.3** (форматы и допустимые значения: длина наименования, перечень MIME, предельный размер содержимого), **4.10** (статусы жизненного цикла сверх `draft`/`published`), **5.3** (сроки хранения и глубина истории версий).
- До закрытия вопросов: таблицы, ограничения и миграции делаются полностью; лимиты выносятся в конфигурацию вне образа, принятые значения помечаются предварительными.

### 7. Определение готовности (DoD)
1. Схема и репозиторий M1 в ветке; миграция прямого и обратного хода применяется на чистой и непустой БД, повторный запуск не меняет схему и не завершается ошибкой.
2. Тесты: `NOT NULL`, `CHECK (state)`, `UNIQUE (material_id, version_no)`, запрет `UPDATE` опубликованной версии, пустая выдача черновика в области участника.
3. Журнал: записи `schema.migrate`, создания и отказа присутствуют с пятью обязательными атрибутами.
4. Права: внутренние операции отклоняются без прав `material.add`/`material.publish` (401 без аутентификации, 403 без права).
5. Выписка DDL и описание данных приложены к поставке, отсутствие полей секретов подтверждено; выполнена проверка перезапуска и восстановления из резервной копии с чтением ранее сохранённых записей.

### 8. Тест-кейсы

| ID | Тип | Предусловие | Шаги | Ожидаемый результат | Пункт ТЗ |
|---|---|---|---|---|---|
| K-66-01 | позитивный | чистая БД | применить миграцию, затем применить повторно | созданы `material`, `material_version` с полями раздела 2; второй запуск без ошибок, `schema_version` не изменился; в журнале две записи `schema.migrate`/«успех» | 3.1, 7 |

## P22-67 — Результат 1: добавление материала и хранение содержимого и реквизитов в платформе

**Основание:** ТЗ CA_PS-2026-10, п. 3.1 (+ общее ТЗ, раздел 7.2)
**Модуль:** M1 · **Компонент:** core

### 1. Что реализовать
1. Создание материала вместе с черновиком версии 1 и создание нового черновика версии существующего материала с номером `max+1`.
2. Сохранение и замену содержимого версии в объектном хранилище M16 по ключу `material_version_id` с расчётом контрольной суммы, размера и типа; изменение реквизитов и содержимого — только при `state='draft'`, по опубликованной версии отказ 409 с указанием создать новую версию.
3. Повторное открытие сохранённой версии оператором: чтение реквизитов и выдача содержимого, совпадающего по контрольной сумме с сохранённым.
4. Валидацию полноты (неполный ввод возвращает перечень незаполненных полей, записи не создаются, признак успеха не возвращается — мес. ТЗ п. 3.2), идемпотентность создания по `Idempotency-Key` и проверку прав `material.add`/`material.read` в обработчике — одинаково для вызова из интерфейса и напрямую.

### 2. Данные
Новых сущностей не вводится — используются поля раздела P22-66; заполняются `content_mime`, `content_size`, `content_checksum`, `updated_at`. Добавляется служебная таблица идемпотентности:

| Поле | Тип | Обязательность | Правило заполнения | Источник |
|---|---|---|---|---|
| `idempotency_record.key` | text | да | значение заголовка `Idempotency-Key`; уникален в пределах субъекта | `web-admin` |
| `idempotency_record.principal_id` | uuid → `principal` | да | субъект сессии | M11 |
| `idempotency_record.result_ref`, `created_at` | uuid, timestamptz | да | идентификатор созданной версии; время сервера UTC, срок хранения ключа уточняется (вопрос 7.3 реестра) | платформа |

### 3. Интерфейс (API)

| Метод и путь | Назначение | Кто вызывает | Требуемое право | Коды ответов, включая отказ в доступе |
|---|---|---|---|---|
| `POST /api/materials` | создать материал и черновик версии 1 | `web-admin` (оператор) | `material.add` | 201, 400, 401 (без аутентификации), 403 (профиль чтения, участник), 409 (повтор ключа), 422 (неполные реквизиты) |
| `POST /api/materials/{id}/versions` | создать новый черновик версии | `web-admin` | `material.add` | 201, 401, 403, 404, 409, 422 |
| `PUT /api/materials/{id}/versions/{v}` и `.../content` | изменить реквизиты черновика; сохранить или заменить содержимое | `web-admin` | `material.add` | 200, 401, 403, 404, 409 (версия опубликована), 413/422 (размер и тип; пороги уточняются, вопрос 7.3) |
| `GET /api/materials/{id}/versions/{v}` и `.../content` | повторное открытие версии: реквизиты и содержимое | `web-admin` | `material.read` | 200, 401, 403, 404 (черновик вне области оператора) |
| `GET /api/materials` | перечень материалов и версий с состоянием | `web-admin`, профиль чтения | `material.read` | 200, 401, 403 |

Профиль чтения получает 200 только по `GET`; по всем изменяющим методам — 403 (`docs/arch/04-bezopasnost-i-privacy.md`, п. 1.2, инвариант 3).

### 4. Правила и инварианты
1. Содержимое и реквизиты хранятся в платформе, оператор может повторно открыть сохранённую версию — мес. ТЗ п. 3.1.
2. Создаваемая версия всегда получает `state='draft'`; публикация — отдельная операция (P22-68); изменение содержимого допустимо только для черновика — И-01, п. 3.1, общее ТЗ 7.2, 10.
3. Права на добавление ограничены, проверка выполняется на стороне приложения — И-11, мес. ТЗ пп. 3.1, 4.
4. Запрос без аутентификации отклоняется 401 до выполнения прикладной логики — мес. ТЗ п. 4, проверка 4 п. 8.
5. Неполный ввод не создаёт запись и не обозначается как успешный, ошибка отображается понятно (мес. ТЗ п. 3.2); черновик не выдаётся участнику ни как реквизиты, ни как содержимое (И-01, проверка 3 п. 8).

### 5. Журналирование
Операции `material.create`, `material_version.create`, `material_version.update`, `material_version.content.put`, `material_version.read`, `material_version.content.read` с атрибутами: пользователь, время, объект (`material_id`, `material_version_id`), операция, результат (при отказе — причина: нет аутентификации, нет права, версия опубликована, неполные реквизиты). Не пишутся: содержимое материала и файл, заголовок `Authorization`, пароли и токены сессии (мес. ТЗ п. 4).

### 6. Зависимости и блокировки
- Предшественники: P22-66 (схема), P22-74 (аутентификация и права), P22-76 (журнал), P22-64 (стенд), P22-63 и P22-65 (контрольные данные, безопасный материал). Потребители: P22-68, P22-69.
- Вопросы реестра: **7.3** (длина наименования, перечень MIME, предельный размер содержимого, срок хранения ключей идемпотентности), **5.3** (глубина хранения версий).
- До закрытия вопросов: операции и валидация реализуются полностью, лимиты берутся из конфигурации; в тестах используются предварительные значения, помеченные к подтверждению.

### 7. Определение готовности (DoD)
1. Эндпоинты раздела 3 реализованы, OpenAPI обновлён; миграция таблицы идемпотентности применяется в обе стороны.
2. Тесты: создание и повторное открытие; 401 без токена; 403 для профиля чтения и участника; 409 по опубликованной версии и по повтору ключа; 422 при неполных реквизитах.
3. Журнал: по каждому кейсу раздела 8 есть запись с пятью атрибутами; поиск по контрольному значению токена в журнале совпадений не даёт.
4. Права проверяются в обработчике: прямой вызов API без `web-admin` даёт тот же код отказа.
5. Содержимое читается из M16 по ключу версии, контрольная сумма выданного содержимого равна сохранённой; инструкция оператора «добавление материала и повторное открытие версии» приложена (п. 7 месячного ТЗ).

### 8. Тест-кейсы

| ID | Тип | Предусловие | Шаги | Ожидаемый результат | Пункт ТЗ |
|---|---|---|---|---|---|
| K-67-01 | позитивный | сессия профиля оператора | `POST /api/materials` с наименованием, владельцем, реквизитами | 201, в теле `material_id`, `material_version_id`, `version_no=1`, `state='draft'`; в БД одна строка версии; в журнале `material.create`/«успех» | 3.1 |

## P22-68 — Результат 1: публикация версии и разграничение прав на добавление и публикацию

**Основание:** ТЗ CA_PS-2026-10, пп. 3.1 и 4 (+ общее ТЗ, разделы 7.2, 10)
**Модуль:** M1 · **Компонент:** core

### 1. Что реализовать
1. Публикацию версии (`POST /api/materials/{id}/versions/{v}/publish`): проверку полноты реквизитов, переход `draft → published`, фиксацию `published_at` и `published_by`, переключение `material.current_published_version_id` — в одной транзакции.
2. Запрет повторной публикации опубликованной версии (409, `published_at` не изменяется, повторное событие не формируется) и блокировку изменения опубликованной версии в обработчике и в БД (409).
3. Выдачу версий, допустимых для назначения (только `published`), как контракт M1 → M2, запрет выдачи черновика участнику во всех операциях чтения M1 и публикацию события `material.published` (`material_id`, `version`, `owner`, `published_at`) для M2 и M12 — отметка времени для норматива 5 минут (общее ТЗ 7.3).
4. Разграничение прав на уровне приложения: раздельные права `material.add` и `material.publish`; профиль чтения не выполняет ни одной изменяющей операции.

### 2. Данные
Новых таблиц не вводится; заполняются поля раздела P22-66:

| Поле | Тип | Обязательность | Правило заполнения | Источник |
|---|---|---|---|---|
| `material_version.state` | enum | да | `published` после успешной публикации; обратный переход не предусмотрен | платформа |
| `material_version.published_at`, `published_by` | timestamptz, uuid → `principal` | да при `state='published'` | время сервера UTC в момент фиксации перехода (однократно); субъект сессии с правом `material.publish` | платформа, M11 |
| `material.current_published_version_id` | uuid → `material_version` | нет | идентификатор последней опубликованной версии | платформа |
| событие `material.published` | запись шины | да | `material_id`, `version`, `owner`, `published_at`; ключ `(material_version_id)` — повтор не создаёт второго события | M1 → M2, M12 |

### 3. Интерфейс (API)

|---|---|---|---|---|
| `POST /api/materials/{id}/versions/{v}/publish` | публикация версии | `web-admin` (оператор) | `material.publish` | 200, 401 (без аутентификации), 403 (профиль чтения, участник, оператор без `material.publish`), 404, 409 (уже опубликована), 422 (неполные реквизиты) |
| `GET /api/materials/{id}/versions?state=published` | перечень опубликованных версий | `web-admin`, профиль чтения | `material.read` | 200 (черновики не возвращаются), 401, 403 |

### 4. Правила и инварианты
1. Опубликованная версия доступна для назначения — мес. ТЗ п. 3.1, проверка 1 п. 8, И-01.
2. Черновик участнику не выдаётся ни как назначение, ни как содержимое — мес. ТЗ пп. 3.1, 3.2, проверка 3 п. 8, И-01.
3. Права на добавление и публикацию ограничены и разделены (`material.add` ≠ `material.publish`); профиль чтения не изменяет материал и настройки — мес. ТЗ пп. 3.1, 4, проверка 4 п. 8.
4. Полномочия проверяются на стороне приложения: прямой вызов API в обход интерфейса даёт тот же отказ — И-11, мес. ТЗ п. 4.
5. Повторная публикация той же версии не выполняется и не обозначается как успешная, публикация неполного черновика отклоняется с перечнем полей (мес. ТЗ пп. 3.1, 3.2); опубликованная версия неизменяема, ранее созданные назначения продолжают ссылаться на свою версию (И-01, общее ТЗ 7.2).

### 5. Журналирование
Операции: `material_version.publish` (успех/отказ, с предыдущим и новым значением `state`), повторная публикация (отказ 409), `material_version.read`, отказ `material_version.update` по опубликованной версии, отказы по аутентификации и праву. Атрибуты: пользователь, время, объект (`material_id`, `material_version_id`, `version_no`), операция, результат. Не пишутся: содержимое материала, токены сессии, заголовки авторизации (мес. ТЗ п. 4).

### 6. Зависимости и блокировки
- Предшественники: P22-66 (схема и неизменяемость), P22-67 (черновик и содержимое), P22-74 (права `material.add`, `material.publish`, профиль чтения), P22-76 (журнал). Потребители: P22-70 (назначение), P22-69 (интерфейс), P22-73 (норматив от `published_at`).
- Вопросы реестра: **7.3** (допустимые значения реквизитов, проверяемых при публикации), **4.10** (статус «не актуальна» и снятие публикации в октябре не реализуются), **6.1** (точка t0 норматива 5 минут — считается ли началом отсчёта `published_at`), **5.4** (кто, кроме оператора, вправе читать черновики).
- До закрытия вопросов: публикация, разграничение прав и событие `material.published` с отметкой времени реализуются полностью; трактовка t0 закрепляется в Программе и методике испытаний (P22-38).

### 7. Определение готовности (DoD)
1. Эндпоинт публикации и эндпоинты выдачи опубликованных версий реализованы, OpenAPI обновлён; миграции сверх P22-66 не требуются либо применяются в обе стороны.
2. Тесты: публикация; повторная публикация (409); публикация профилем чтения и субъектом без `material.publish` (403); прямой вызов API в обход UI (403); запрос без аутентификации (401); неполный черновик (422); недоступность черновика участнику; изменение опубликованной версии (409).
3. Журнал: по каждой публикации и каждому отказу есть запись с пятью атрибутами и сменой состояния; секретов в записях нет.
4. Событие `material.published` формируется один раз на версию (проверено повторным вызовом).

## P22-70 — Результат 2: программное назначение материала локальной тестовой группе

**Основание:** ТЗ CA_PS-2026-10, п. 3.2 (+ общее ТЗ, раздел 7.3)
**Модуль:** M2 · **Компонент:** core

### 1. Что реализовать
1. Локальную тестовую группу (`test_group`, `test_group_member`) в объёме контрольных данных (мес. ТЗ п. 5: одна группа и отдельный неназначенный участник).
2. Назначение (`POST /api/assignments`): вход — `material_version_id` и `group_id`, выход — по одному назначению на каждого члена группы; версия проверяется через контракт M1 → M2 и должна быть `published`; операция атомарна — при недопустимой версии или участнике не создаётся ни одно назначение и признак успеха не возвращается (мес. Область видимости и управление: участник получает только свои назначения (`GET /api/my/assignments`), назначения, статусы и результаты других участников не выдаются; оператор видит назначения материала и состав группы, может отменить назначение; повторное назначение не создаёт дубля (ограничение уникальности активного назначения).

## P22-74 — Аутентификация и профили доступа: оператор и чтение

**Основание:** ТЗ CA_PS-2026-10, п. 4 (+ общее ТЗ, раздел 10)
**Модуль:** M11 · **Компонент:** core

### 1. Что реализовать
1. Локальные учётные записи и вход по паролю (`POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`) с серверными сессиями: хранение хеша токена, срок действия, отзыв; передача токена только по TLS (п. 4 месячного ТЗ, P22-75). На октябрь — локальные учётные записи по п. 5 месячного ТЗ; корпоративный SSO — вопрос 1.6 реестра.
2. Профили октябрьского объёма — `оператор` (добавление, публикация, назначение), `чтение` (только просмотр), `участник` (свои назначения и свой результат) — как подмножество матрицы `docs/arch/04-bezopasnost-i-privacy.md`, п. 1.2; каталог прав `material.add`, `material.publish`, `material.read`, `assignment.create`, `assignment.read_all`, `assignment.read_own`, `completion.read_own`, `completion.read_all`, `audit.read` и привязки `role_permission`, `role_binding`.
3. Единую серверную точку проверки полномочий `M11.check` с обязательным вызовом в каждом обработчике M1 и M2 до выполнения прикладной логики: решение принимается по серверной привязке роли, данные запроса (`X-Role`, поля тела) игнорируются; 401 — для запроса без аутентификации, с неизвестным, истёкшим или отозванным токеном, 403 — для субъекта без требуемого права, в едином формате без раскрытия существования объекта; изменение своей роли и выдача прав самому себе запрещены.
4. Журналирование входа, выхода, отказов и проверок полномочий с исключением пароля и токена из журнала, трассировки, метрик и сообщений об ошибках; матрицу раздела 4 как параметризованный автотест «операция × профиль × ожидаемый код».

### 4. Правила и инварианты
1. Доступ к интерфейсу и прикладным операциям — только после аутентификации; неавторизованный запрос отклоняется — мес. ТЗ п. 4, проверка 4 п. 8.
2. Профиль оператора выполняет только разрешённые изменения; профиль чтения просматривает результаты без права изменять настройки и данные — мес. ТЗ п. 4, инвариант 3 матрицы прав.
3. Полномочия проверяются на стороне приложения, а не только в интерфейсе; решение принимается по серверной привязке роли, значения из тела, параметров и заголовков (`X-Role`, `role`, `is_admin`) игнорируются — И-11, мес. ТЗ п. 4.
4. Участник видит только свои назначения и свой результат — И-02, мес. ТЗ пп. 3.2, 4.
5. Пароли, ключи и токены не включаются в аудит и технические журналы (мес. ТЗ п. 4, И-09); изменение собственной роли, выдача прав самому себе и изменение записей журнала запрещены (общее ТЗ 10, инварианты 1 и 6 матрицы); дефект, допускающий обход разграничения доступа, устраняется до приёмки (мес. ТЗ п. 4).

### 5. Журналирование
Операции: `auth.login` (успех/отказ с логином и причиной), `auth.logout`, `auth.token.rejected` (нет токена, истёк, отозван), `authz.denied` (субъект, требуемое право, объект, операция), `authz.allowed` по изменяющим операциям, `role_binding.change` (отказ). Атрибуты: пользователь либо `anonymous`, время, объект (эндпоинт и идентификатор объекта), операция, результат. Не пишутся в журнал, трассировку, метрики и сообщения об ошибках: пароль, его длина и состав, значение сессионного токена, заголовок `Authorization`, содержимое `Set-Cookie` (мес. ТЗ п. 4, И-09).

### 6. Зависимости и блокировки
- Предшественники: P22-64 (стенд), P22-65 (локальные учётные записи контрольных данных), P22-75 (TLS и секреты вне кода и образов), P22-76 (журнал). Потребители: P22-67, P22-68, P22-70, P22-71, P22-72, P22-73, P22-76.
- Вопросы реестра: **1.6** (способ аутентификации: корпоративный SSO или локальные учётные записи — на октябрь приняты локальные по п. 5 месячного ТЗ), **5.4** (ролевая модель видимости персональных результатов и рейтингов), **5.8** (доступ администратора платформы к персональным результатам), **3.3** (роль «уполномоченного оператора» и фиксация подтверждения — за пределами октября), **7.5** (менеджер секретов и ротация), **7.3** (TTL сессии, политика пароля, порог блокировки).
- До закрытия вопросов: локальная аутентификация, три профиля, серверная проверка полномочий и матрица раздела 4 реализуются полностью; внешний провайдер подключается как дополнительный способ аутентификации без изменения модели прав; TTL и политика пароля остаются в конфигурации вне образа.

### 7. Определение готовности (DoD)
1. Эндпоинты раздела 3 реализованы, OpenAPI обновлён; для каждого эндпоинта P22-67, P22-68, P22-70 указано требуемое право.

3. Матрица раздела 4 реализована как параметризованный автотест (операция × профиль × код) и проходит по всем ячейкам; отдельные тесты — обход UI, подмена заголовка роли, истёкшая и отозванная сессия.

| K-74-09 | граничный | действующая сессия | выполнить `logout` и повторить запрос с тем же токеном; отдельно — запрос с токеном, у которого `expires_at` в прошлом | 401 в обоих случаях; `session.revoked_at` заполнен; повторный вход выдаёт новую сессию (TTL уточняется, вопрос 7.3 реестра) | 4 |
| K-74-10 | негативный | учётная запись в состоянии `blocked` | `POST /api/auth/login` с верным паролем | доступ не предоставлен (423/401); сессия не создана; в журнале «отказ: учётная запись заблокирована» | 4 |
| K-74-11 | позитивный | выполнены K-74-01…K-74-10 | выгрузить журнал за период, искать контрольный пароль, выданный токен и значение `Authorization` | по каждой операции есть запись с пользователем, временем, объектом, операцией и результатом; совпадений по паролю и токену нет ни в журнале, ни в технических логах, ни в выгрузке | 4 |

### 9. Что не входит
Полная ролевая модель (администратор платформы, оператор кампаний, методолог, аналитик результатов, техническая учётная запись интеграции), разграничение доступа к персональным результатам и рейтингам, маскирование — P22-87 (общее ТЗ 10, 7.13), вне октябрьского объёма (мес. ТЗ п. 5). Корпоративный SSO и управление учётными записями — вне границ проекта (общее ТЗ, раздел 3; вопрос 1.6 реестра). TLS и менеджер секретов — P22-75; журнал с контролем целостности — P22-76 и P22-88.
