# Постановки для разработки: ядро результатов 1 и 2 (CA_PS-2026-10)

Задачи Senior-разработчика П.22 октябрьского объёма: P22-66, P22-67, P22-68, P22-70, P22-74.
Источники: `docs/source/tz-ca_ps-2026-10.txt` (месячное ТЗ), `docs/arch/02-domennaya-model.md`
(сущности, состояния, инварианты И-01…И-16), `docs/arch/01-moduli-i-granicy.md` (модули M1, M2,
M11, M12, события, внешний API), `docs/arch/04-bezopasnost-i-privacy.md` (роли, матрица прав,
аудит), `docs/05-otkrytye-voprosy.md` (реестр открытых вопросов).

Общие соглашения для всех разделов: ядро — модульный монолит `core`; изменяющие запросы несут
`Idempotency-Key`; аутентификация обязательна для всех прикладных операций (мес. ТЗ п. 4);
журнал ведёт M12 (задача P22-76) по вызову из прикладного модуля; состав журнальной записи —
пользователь, время, объект, операция, результат (мес. ТЗ п. 4). Значения, которых нет в ТЗ
(форматы, допустимые значения, лимиты, TTL), помечены как уточняемые с номером вопроса реестра.

## P22-66 — Результат 1: схема данных учебного материала — наименование, владелец, версия, состояние

**Основание:** ТЗ CA_PS-2026-10, п. 3.1 (+ п. 7 — схема данных входит в состав передаваемого результата; общее ТЗ, раздел 7.2)
**Модуль:** M1 · **Компонент:** core

### 1. Что реализовать
1. Таблицу `material` — учебный материал: идентификатор, наименование, владелец, ссылка на текущую опубликованную версию.
2. Таблицу `material_version` — версия материала: номер версии, состояние (`draft`/`published`), реквизиты содержимого, автор, время создания и публикации.
3. Монотонную нумерацию версий в пределах материала: ограничение `UNIQUE (material_id, version_no)`.
4. Ограничение неизменяемости опубликованной версии: запрет `UPDATE` полей содержимого и реквизитов при `state='published'` (правило БД + проверка в репозитории M1).
5. Ограничение состояний: `CHECK (state IN ('draft','published'))`; переходы — только `draft → published` (`docs/arch/02-domennaya-model.md`, п. 2.1).
6. Представление (или параметризованный запрос) выдачи версий участнику, в которое версии в состоянии `draft` не попадают по определению (И-01).
7. Миграции прямого и обратного хода, идемпотентные при повторном применении, с фиксацией версии схемы.
8. Выписку DDL и описание данных для передачи Заказчику (п. 7 месячного ТЗ) — без полей для паролей, токенов, MFA-кодов (И-09).

### 2. Данные
Сущности «Учебный материал» и «Версия учебного материала» из `docs/arch/02-domennaya-model.md`, п. 1. В октябре создаются поля:

| Поле | Тип | Обязательность | Правило заполнения | Источник |
|---|---|---|---|---|
| `material.id` | uuid | да | генерируется платформой | платформа |
| `material.name` | text | да | непустое после обрезки пробелов; предельная длина уточняется (вопрос 7.3 реестра) | ввод оператора |
| `material.owner_principal_id` | uuid → `principal` | да | субъект с правом `material.add`; по умолчанию автор черновика | M11 (P22-74) |
| `material.current_published_version_id` | uuid → `material_version` | нет | заполняется при публикации, иначе `NULL` | P22-68 |
| `material.created_at` / `created_by` | timestamptz / uuid | да | время сервера UTC / субъект сессии | платформа, M11 |
| `material_version.id` | uuid | да | генерируется платформой | платформа |
| `material_version.material_id` | uuid → `material` | да | — | платформа |
| `material_version.version_no` | integer | да | 1 для первой версии, далее `max+1`; уникален в пределах материала | платформа |
| `material_version.state` | enum (`draft`,`published`) | да | при создании всегда `draft` | платформа |
| `material_version.content_ref` | text | да | ключ объекта в хранилище M16, равен `material_version.id` | M16 |
| `material_version.content_mime` | text | да | из перечня допустимых типов; перечень уточняется (вопрос 7.3 реестра) | ввод оператора |
| `material_version.content_size` | bigint | да | фактический размер сохранённого объекта; предельный размер уточняется (вопрос 7.3 реестра) | M16 |
| `material_version.content_checksum` | text | да | контрольная сумма содержимого, считается при сохранении; служит признаком неизменности | платформа |
| `material_version.author_principal_id` | uuid → `principal` | да | субъект, создавший черновик | M11 |
| `material_version.created_at` / `updated_at` | timestamptz | да / да | время сервера UTC; `updated_at` не меняется после публикации | платформа |
| `material_version.published_at` / `published_by` | timestamptz / uuid | нет (обязательны при `state='published'`) | заполняются один раз при публикации | P22-68 |

Поля категорирования, статуса актуальности и сроков обязательного ознакомления (7.2) в октябре не создаются — расширение по `docs/arch/02-domennaya-model.md`, п. 6.

### 3. Интерфейс (API)
Собственных HTTP-эндпоинтов задача не вводит: API добавления и чтения — P22-67, публикации — P22-68. Реализуется внутренний контракт модуля M1:

| Метод и путь | Назначение | Кто вызывает | Требуемое право | Коды ответов, включая отказ в доступе |
|---|---|---|---|---|
| внутр. `M1.createDraft(material, version)` | создание материала и черновика версии | M1 (обработчик P22-67) | `material.add` | ок / `VALIDATION_FAILED` / `FORBIDDEN` (транслируется в 403) |
| внутр. `M1.getVersion(id, scope)` | чтение версии с учётом области видимости | M1, M2 | `material.read` (оператор) либо `material.read_assigned` (участник) | ок / `NOT_FOUND` при `draft` и области участника |
| внутр. `M1.listAssignableVersions(material_id)` | перечень версий, допустимых для назначения (только `published`) | M2 (P22-70) | `material.read` | ок (черновики не возвращаются — И-01) |
| внутр. `M1.markPublished(version_id, principal)` | перевод в `published` | M1 (обработчик P22-68) | `material.publish` | ок / `ALREADY_PUBLISHED` (409) / `FORBIDDEN` (403) |

### 4. Правила и инварианты
1. Версия хранит наименование (через материал), владельца, номер версии и состояние — мес. ТЗ п. 3.1.
2. Содержимое и реквизиты материала хранятся в платформе — мес. ТЗ п. 3.1.
3. Опубликованная версия неизменяема; изменение содержимого выполняется созданием новой версии — И-01, общее ТЗ 7.2, 10.
4. Черновик недоступен в области видимости участника на уровне запроса, а не только интерфейса — И-01, И-11, мес. ТЗ пп. 3.1, 4.
5. Номер версии монотонен в пределах материала — `docs/arch/01-moduli-i-granicy.md`, п. 6.2.
6. Схема не содержит полей для паролей, MFA-кодов, PIN и токенов — И-09, мес. ТЗ п. 4.
7. Данные отделены от приложения: перезапуск не приводит к потере сохранённых записей — мес. ТЗ п. 4, проверка 5 п. 8.

### 5. Журналирование
Записываются (через M12): применение миграции (объект — версия схемы, операция `schema.migrate`, результат); создание материала и черновика; отказ по ограничению целостности (операция, объект, результат «отказ», код ограничения). Атрибуты: пользователь или техническая учётная запись, время, объект (`material_id`, `material_version_id`), операция, результат. В журнал не пишутся: содержимое материала, значения любых секретов, параметры подключения к БД (мес. ТЗ п. 4, И-09).

### 6. Зависимости и блокировки
- Предшественники: P22-63 (согласование контрольных данных и форматов), P22-64 (стенд и контур развёртывания).
- Вопросы реестра: **7.3** (контрольные данные, форматы и допустимые значения месячного объёма — предельная длина наименования, перечень MIME, предельный размер содержимого), **4.10** (состав жизненного цикла — статусы сверх `draft`/`published`), **5.3** (сроки хранения и глубина истории).
- До закрытия вопросов можно: создавать таблицы, ограничения и миграции; значения лимитов вынести в конфигурацию (не в код), значения по умолчанию помечать как предварительные.

### 7. Определение готовности (DoD)
1. Код схемы и репозитория M1 в ветке, миграция прямого и обратного хода применяется на чистой и на непустой БД.
2. Повторное применение миграции не изменяет схему и не завершается ошибкой.
3. Тесты: ограничения `NOT NULL`, `CHECK (state)`, `UNIQUE (material_id, version_no)`, запрет `UPDATE` опубликованной версии, пустая выдача черновика в области участника.
4. Журнал: записи `schema.migrate`, создания и отказа присутствуют с пятью обязательными атрибутами.
5. Права: вызовы внутреннего контракта отклоняются без прав `material.add`/`material.publish`.
6. Выписка DDL и описание данных приложены к поставке (п. 7 месячного ТЗ); подтверждено отсутствие полей секретов.
7. Проверка перезапуска контейнера БД: ранее сохранённые материал и версия читаются без расхождений.

## P22-67 — Результат 1: добавление материала и хранение содержимого и реквизитов в платформе

**Основание:** ТЗ CA_PS-2026-10, п. 3.1 (+ общее ТЗ, раздел 7.2)
**Модуль:** M1 · **Компонент:** core

### 1. Что реализовать
1. Создание материала вместе с черновиком версии 1 (`POST /api/materials`) — наименование, владелец, реквизиты содержимого.
2. Создание новой версии-черновика существующего материала (`POST /api/materials/{id}/versions`) с номером `max+1`.
3. Сохранение содержимого версии в объектное хранилище M16 по ключу `material_version_id` с расчётом контрольной суммы и размера.
4. Изменение черновика: наименование, реквизиты, замена содержимого — только для `state='draft'`.
5. Повторное открытие сохранённой версии оператором: чтение реквизитов и выдача содержимого (`GET /api/materials/{id}/versions/{v}`, `GET .../content`).
6. Валидацию полноты реквизитов: неполный ввод возвращает перечень незаполненных полей и не создаёт запись, помеченную успешной (мес. ТЗ п. 3.2 — «неполный результат не обозначается как успешный»).
7. Идемпотентность создания по `Idempotency-Key`: повторный запрос не создаёт вторую запись.
8. Проверку прав на стороне приложения в обработчике, а не в интерфейсе (`material.add`, `material.read`).

### 2. Данные
Новых сущностей не вводится; используются поля из раздела P22-66. Дополнительно заполняются: `material_version.updated_at` (при каждом изменении черновика), `content_mime`, `content_size`, `content_checksum` (при сохранении содержимого), служебная таблица идемпотентности:

| Поле | Тип | Обязательность | Правило заполнения | Источник |
|---|---|---|---|---|
| `idempotency_record.key` | text | да | значение заголовка `Idempotency-Key` | клиент (`web-admin`) |
| `idempotency_record.principal_id` | uuid | да | субъект сессии | M11 |
| `idempotency_record.result_ref` | uuid | да | идентификатор созданной версии | платформа |
| `idempotency_record.created_at` | timestamptz | да | время сервера UTC; срок хранения ключа уточняется (вопрос 7.3 реестра) | платформа |

### 3. Интерфейс (API)

| Метод и путь | Назначение | Кто вызывает | Требуемое право | Коды ответов, включая отказ в доступе |
|---|---|---|---|---|
| `POST /api/materials` | создать материал и черновик версии 1 | `web-admin` (оператор) | `material.add` | 201, 400, 401 (без аутентификации), 403 (профиль чтения, участник), 409 (повтор ключа), 422 (неполные реквизиты) |
| `POST /api/materials/{id}/versions` | создать новый черновик версии | `web-admin` | `material.add` | 201, 401, 403, 404, 409, 422 |
| `PUT /api/materials/{id}/versions/{v}` | изменить реквизиты черновика | `web-admin` | `material.add` | 200, 401, 403, 404, 409 (версия опубликована), 422 |
| `PUT /api/materials/{id}/versions/{v}/content` | сохранить/заменить содержимое черновика | `web-admin` | `material.add` | 200, 401, 403, 404, 409 (версия опубликована), 413/422 (размер, тип — пороги уточняются, вопрос 7.3) |
| `GET /api/materials/{id}/versions/{v}` | повторное открытие версии: реквизиты | `web-admin` | `material.read` | 200, 401, 403, 404 (черновик вне области оператора) |
| `GET /api/materials/{id}/versions/{v}/content` | повторное открытие версии: содержимое | `web-admin` | `material.read` | 200, 401, 403, 404 |
| `GET /api/materials` | перечень материалов и версий с состоянием | `web-admin` | `material.read` | 200, 401, 403 |

Профиль чтения получает 200 только по `GET`; по всем изменяющим методам — 403 (`docs/arch/04-bezopasnost-i-privacy.md`, п. 1.2, инвариант 3).

### 4. Правила и инварианты
1. Содержимое и реквизиты материала хранятся в платформе; оператор может повторно открыть сохранённую версию — мес. ТЗ п. 3.1.
2. Создаваемая версия всегда получает `state='draft'`; публикация выполняется отдельной операцией — И-01, п. 3.1.
3. Изменение содержимого допустимо только для черновика; по опубликованной версии — 409 с указанием создать новую версию — И-01, общее ТЗ 7.2, 10.
4. Права на добавление ограничены: проверка в обработчике API, одинаковая для вызова из интерфейса и напрямую — И-11, мес. ТЗ пп. 3.1, 4.
5. Запрос без аутентификации отклоняется (401) до выполнения прикладной логики — мес. ТЗ п. 4, проверка 4 п. 8.
6. Неполный ввод не создаёт запись и не возвращает признак успеха; ошибка отображается понятно — мес. ТЗ п. 3.2.
7. Повторное открытие возвращает содержимое, совпадающее по контрольной сумме с сохранённым — мес. ТЗ п. 3.1.

### 5. Журналирование
Операции `material.create`, `material_version.create`, `material_version.update`, `material_version.content.put`, `material_version.read`, `material_version.content.read` — с атрибутами: пользователь, время, объект (`material_id`, `material_version_id`), операция, результат («успех»/«отказ» с причиной: нет аутентификации, нет права, версия опубликована, неполные реквизиты). В журнал не пишутся: содержимое материала и файл, значение `Authorization`, пароли и токены сессии (мес. ТЗ п. 4).

### 6. Зависимости и блокировки
- Предшественники: P22-66 (схема), P22-74 (аутентификация и права `material.add`/`material.read`), P22-76 (журнал), P22-64 (стенд), P22-63/P22-65 (контрольные данные и безопасный материал).
- Вопросы реестра: **7.3** (форматы и допустимые значения: длина наименования, перечень MIME, предельный размер содержимого, срок хранения ключей идемпотентности), **5.3** (глубина хранения версий).
- До закрытия вопросов можно: реализовать операции и валидацию, вынести лимиты в конфигурацию M16/приложения; в тестах использовать предварительные значения и отметить их как подлежащие подтверждению.

### 7. Определение готовности (DoD)

## P22-68 — Результат 1: публикация версии и разграничение прав на добавление и публикацию

**Основание:** ТЗ CA_PS-2026-10, п. 3.1 и п. 4 (+ общее ТЗ, разделы 7.2, 10)
**Модуль:** M1 · **Компонент:** core

### 1. Что реализовать
1. Операцию публикации версии (`POST /api/materials/{id}/versions/{v}/publish`): проверка полноты реквизитов, перевод `draft → published`, фиксация `published_at`, `published_by`.
2. Переключение `material.current_published_version_id` на опубликованную версию в одной транзакции с переходом состояния.
3. Запрет повторной публикации уже опубликованной версии (409, `published_at` не изменяется, повторное событие не публикуется).
4. Выдачу перечня версий, допустимых для назначения: только `state='published'` (контракт M1 → M2).
5. Публикацию доменного события `material.published` (`material_id`, `version`, `owner`, `published_at`) для M2 и M12 — основание отсчёта норматива 5 минут (общее ТЗ 7.3).
6. Разграничение прав на уровне приложения: отдельные права `material.add` и `material.publish`; профиль чтения не выполняет ни одну из операций.
7. Блокировку изменения опубликованной версии на уровне обработчика и БД (409) — изменение только созданием новой версии.
8. Запрет выдачи черновика участнику во всех операциях чтения M1 (И-01).

### 2. Данные
Новых таблиц не вводится. Заполняются поля из раздела P22-66: `material_version.state`, `published_at`, `published_by`, `material.current_published_version_id`.

| `material_version.published_by` | uuid → `principal` | да при `state='published'` | субъект сессии с правом `material.publish` | M11 (P22-74) |

### 4. Правила и инварианты
1. Опубликованная версия доступна для назначения — мес. ТЗ п. 3.1, проверка 1 п. 8, И-01.
2. Черновик участнику не выдаётся ни как назначение, ни как содержимое — мес. ТЗ пп. 3.1, 3.2, проверка 3 п. 8, И-01.
3. Права на добавление и публикацию ограничены и разделены (`material.add` ≠ `material.publish`) — мес. ТЗ пп. 3.1, 4.
4. Профиль чтения не изменяет материал и настройки — мес. ТЗ п. 4, проверка 4 п. 8 (`docs/arch/04-bezopasnost-i-privacy.md`, инвариант 3 матрицы).
5. Полномочия проверяются на стороне приложения: прямой вызов API в обход интерфейса даёт тот же отказ — И-11, мес. ТЗ п. 4.
6. Повторная публикация той же версии не выполняется и не считается успешной — мес. ТЗ п. 3.2 (неполный/недопустимый результат не обозначается как успешный).
7. Публикация неполного черновика отклоняется с перечнем незаполненных реквизитов — мес. ТЗ пп. 3.1, 3.2.
8. Опубликованная версия неизменяема; ранее созданные назначения продолжают ссылаться на свою версию — И-01, общее ТЗ 7.2.

**Основание:** ТЗ CA_PS-2026-10, п. 3.2 (+ общее ТЗ, раздел 7.3)
**Модуль:** M2 · **Компонент:** core

### 1. Что реализовать
1. Локальную тестовую группу: сущности «группа» и «член группы» в объёме контрольных данных месячного ТЗ (п. 5: одна группа и отдельный неназначенный участник).
2. Операцию назначения (`POST /api/assignments`): вход — `material_version_id` и `group_id`; на выходе — по одному назначению на каждого члена группы.
3. Проверку, что назначается только опубликованная версия (через контракт M1 → M2); назначение черновика отклоняется.
4. Атомарность: при недопустимом участнике или версии не создаётся ни одно назначение; ответ не содержит признака успеха (мес. ТЗ п. 3.2).

8. Идемпотентность: повторное назначение той же версии той же группе не создаёт дублей (ограничение уникальности по активному назначению).

### 4. Правила и инварианты
1. Назначение создаётся только для опубликованной версии; черновик не назначается — И-01, мес. ТЗ пп. 3.1, 3.2, проверка 3 п. 8.
2. Неназначенный пользователь не получает ни назначение, ни результаты других участников — И-02, мес. ТЗ пп. 3.2, 4, проверка 3 п. 8.
3. Назначение выполняет уполномоченный оператор; профиль чтения назначение не создаёт — мес. ТЗ п. 4.
4. Назначение доступно работнику не позднее 5 минут после публикации — И-03, мес. ТЗ п. 3.2 (точка t0 и число замеров уточняются, вопрос 6.1 реестра; реализация P22-73).
5. Неполный результат не обозначается как успешным: частично выполненное назначение группы откатывается целиком — И-04, мес. ТЗ п. 3.2.
6. Полномочия проверяются на стороне приложения, включая прямые вызовы API — И-11, мес. ТЗ п. 4.
7. Повторное назначение той же версии тому же участнику не создаёт дубля — `docs/arch/01-moduli-i-granicy.md`, п. 3 (идемпотентность M8 → M2 по аналогии).
8. Назначение ссылается на конкретную `material_version_id`; последующая публикация новой версии ранее созданные назначения не переписывает — `docs/arch/01-moduli-i-granicy.md`, п. 6.2.

## P22-74 — Аутентификация и профили доступа: оператор и чтение

**Основание:** ТЗ CA_PS-2026-10, п. 4 (+ общее ТЗ, раздел 10)
**Модуль:** M11 · **Компонент:** core

### 1. Что реализовать
1. Локальные учётные записи (`principal`) и вход по паролю: `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me` (способ аутентификации на октябрь — локальные учётные записи по п. 5 месячного ТЗ; корпоративный SSO — вопрос 1.6 реестра).
2. Серверные сессии: хранение хеша токена, срок действия, отзыв; токен передаётся только по TLS (п. 4 месячного ТЗ).
3. Профили доступа октябрьского объёма: `оператор` (добавление, публикация, назначение), `чтение` (только просмотр), `участник` (только свои назначения и свой результат) — подмножество матрицы `docs/arch/04-bezopasnost-i-privacy.md`, п. 1.2.
4. Каталог прав и привязок: `permission`, `role`, `role_binding`; права — `material.add`, `material.publish`, `material.read`, `assignment.create`, `assignment.read_all`, `assignment.read_own`, `completion.read_all`, `completion.read_own`, `audit.read`.
5. Единую серверную точку проверки полномочий (middleware + явная проверка в обработчике каждой операции M1 и M2); решение принимается по серверной привязке роли, а не по данным запроса.
6. Отказ 401 для запроса без аутентификации, с неизвестным, отозванным или истёкшим токеном — до выполнения прикладной логики.
7. Отказ 403 для аутентифицированного субъекта без требуемого права; единый формат ответа без раскрытия существования объекта.
8. Запрет изменения собственной роли и выдачи прав самому себе (инвариант 6 матрицы, общее ТЗ 10).
9. Журналирование входа, выхода, отказов и всех проверок полномочий с результатом; исключение пароля и токена из журнала, трассировки и сообщений об ошибках.
10. Матрицу проверки прав (раздел 4) как исполняемый тест: таблица «операция × профиль × ожидаемый код» в составе автотестов.

1. Доступ к интерфейсу и прикладным операциям — только после аутентификации; неавторизованный запрос отклоняется — мес. ТЗ п. 4, проверка 4 п. 8.

6. Изменение собственной роли и выдача прав самому себе запрещены — общее ТЗ 10 (инвариант 6 матрицы).
7. Решение о доступе принимается по серверной привязке роли; значения из тела, параметров и заголовков запроса (`X-Role`, `role`, `is_admin`) игнорируются — И-11.

2. Миграции `principal`, `role`, `permission`, `role_permission`, `role_binding`, `session` применяются в обе стороны; привязки прав профилям заданы миграцией.
3. Тесты: матрица раздела 4 реализована как параметризованный автотест (операция × профиль × код), все ячейки проходят; отдельные тесты на обход UI, подмену заголовка роли, истёкшую и отозванную сессию.
4. Журнал: на каждый allow по изменяющей операции и на каждый deny есть запись с пятью атрибутами; поиск по контрольному паролю и по значению выданного токена в журналах, трассировке и выгрузках совпадений не даёт.
5. Права: ни один обработчик M1/M2 не выполняет прикладную логику до вызова `M11.check` (проверено тестом и обзором кода).
6. Секреты и параметры (TTL, политика пароля) читаются из конфигурации вне образа; в коде и образе значений нет (п. 4 месячного ТЗ, P22-75).
7. Инструкция «профили доступа оператора и чтения, вход на стенд» приложена (п. 7 месячного ТЗ).

### 9. Что не входит
Полная ролевая модель (администратор платформы, оператор кампаний, методолог, аналитик результатов, техническая учётная запись интеграции), разграничение доступа к персональным результатам и рейтингам, маскирование — P22-87 (общее ТЗ 10, 7.13), вне октябрьского объёма по п. 5 месячного ТЗ. Корпоративный SSO и управление учётными записями — вне границ проекта (общее ТЗ, раздел 3; вопрос 1.6 реестра). TLS и менеджер секретов — P22-75. Журнал как подсистема с контролем целостности — P22-76 (октябрь) и P22-88 (полный объём).
