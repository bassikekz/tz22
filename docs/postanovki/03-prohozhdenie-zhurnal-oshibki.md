## P22-72 — Результат 2: фиксация прохождения — материал, версия, участник, время

**Основание:** ТЗ CA_PS-2026-10, п. 3.2 (+ п. 4 — сохранность при перезапуске; общее ТЗ, раздел 7.3)
**Модуль:** M2 · **Компонент:** core

### 1. Что реализовать

- Фиксацию прохождения согласованным действием участника: один идемпотентный вызов подтверждения
  по назначению, создающий неизменяемую запись `completion` (И-16).
- Сохранение в записи идентификатора материала, **номера версии материала**, участника и времени
  действия (мес. ТЗ п. 3.2).
- Проверку предусловий на стороне приложения: назначение существует, принадлежит вызывающему
  участнику, ссылается на опубликованную версию, не отменено и не просрочено (И-01, И-02, И-11).
- Признак полноты результата: неполное подтверждение сохраняется со статусом `partial` и не
  обозначается как успешное (И-04).
- Публикацию события `training.completed` для M7/M12 и запись операции в журнал M12 (И-15).
- Хранение записи в Postgres вне образа приложения; перезапуск не приводит к потере данных
  (мес. ТЗ п. 4, проверка 5 п. 8).

### 2. Данные

Таблица `completion` (append-only):

| Поле | Тип | Обязательность | Правило заполнения |
|---|---|---|---|
| `completion_id` | uuid | да | генерируется платформой, первичный ключ |
| `assignment_id` | uuid | да | ссылка на `assignment`; назначение участника-вызывающего |
| `employee_id` | uuid | да | берётся из назначения, не из тела запроса (защита от подмены) |
| `material_id` | uuid | да | копируется из назначения, денормализован для истории |
| `material_version_id` | uuid | да | конкретная опубликованная версия, на которую выдано назначение |
| `version_no` | int | да | номер версии на момент фиксации; историческое значение не перезаписывается |
| `occurred_at` | timestamptz | да | время действия участника, фиксируется сервером |
| `recorded_at` | timestamptz | да | время сохранения записи в хранилище |
| `status` | enum(`completed`,`partial`) | да | `partial` при неполном результате (И-04) |
| `is_complete` | boolean | да | `true` только при `status = completed` |
| `confirmation_action` | enum(`explicit_confirm`) | да | согласованное действие участника; иные значения отклоняются |
| `idempotency_key` | varchar(64) | да | из заголовка запроса; уникален в пределах `assignment_id` |
| `source` | enum(`web-portal`,`api`) | да | канал фиксации |
| `operation_id` | uuid | да | ключ связи с записью журнала M12 |

Ограничения: `UNIQUE (assignment_id) WHERE status = 'completed'` — повторное подтверждение не
создаёт вторую запись; `UNIQUE (assignment_id, idempotency_key)`; запрет `UPDATE`/`DELETE` для
прикладной роли БД (корректировка — только пересмотром результата, 7.20).

### 3. Интерфейс (API)

| Метод и путь | Назначение | Право | Коды ответов |
|---|---|---|---|
| `POST /api/my/assignments/{assignment_id}/completion` | фиксация прохождения участником | `training.complete.own` (работник-участник) | 201, 200 (повтор), 400, 401, 403, 404, 409, 422, 503 |
| `GET /api/my/assignments/{assignment_id}/completion` | собственная запись прохождения | `training.read.own` | 200, 401, 403, 404 |
| `GET /api/completions?employee_id&material_id&material_version_id` | выборка фактов прохождения для оператора | `training.read` (оператор), профиль чтения — только чтение | 200, 400, 401, 403 |

Ответ 201/200: `completion_id`, `assignment_id`, `material_id`, `material_version_id`, `version_no`,
`occurred_at`, `status`, `is_complete`.

### 4. Правила и инварианты

1. И-01: прохождение по версии в состоянии «черновик» невозможно — 409 `STATE_CONFLICT`.
2. И-02: по чужому или отсутствующему назначению — 404 `NOT_FOUND` (без раскрытия существования объекта).
3. Повторное подтверждение идемпотентно: второй вызов возвращает 200 и тот же `completion_id`;
   вызов с тем же `Idempotency-Key` и иным телом — 409 `IDEMPOTENCY_CONFLICT`.
4. Фиксируется именно версия: смена опубликованной версии материала после фиксации не меняет
   `material_version_id` и `version_no` в сохранённой записи.
5. И-16: завершённая запись неизменяема; API изменения и удаления отсутствует.
6. Фиксация прохождения и запись в журнал выполняются в одной транзакции; при недоступности
   журнала операция не подтверждается как успешная (см. P22-79, класс `STORAGE_UNAVAILABLE`).
7. Секреты, содержимое формы и персональные данные сверх перечисленных атрибутов не сохраняются (И-09).

### 5. Отметки времени и измерение норматива

Сохраняются `occurred_at` и `recorded_at`; `occurred_at` используется как `t1` в кейсах P22-73
и как источник `completed_at` события `training.completed`. Собственного норматива у задачи нет.

### 6. Зависимости и блокировки

- P22-66 (схема данных), P22-68 (публикация версии), P22-70 (назначение тестовой группе) — предусловия.
- P22-74 (аутентификация и профили доступа) — источник решения о праве.
- P22-76 — журнал операций; P22-79 — контракт ошибок.
- Вопрос реестра 7.3 — согласование контрольных данных и допустимых значений.

### 7. Определение готовности (DoD)

Кейсы TC-72-01…TC-72-08 пройдены на стенде; запись сохраняется и читается после `docker compose
restart` и после восстановления из копии (проверка 5 п. 8); событие `training.completed`
публикуется один раз на одно прохождение; в журнале присутствует запись операции с результатом;
миграция схемы и индексы включены в поставку.

### 8. Тест-кейсы

| ID | Тип | Предусловие | Шаги | Ожидаемый результат | Пункт ТЗ |
|---|---|---|---|---|---|
| TC-72-01 | позитивный | опубликованная версия v1, участник назначен | `POST .../completion` | 201; в `completion` одна строка с `material_version_id` v1, `version_no=1`, `status=completed`; в журнале `completion.record` / `success` | 3.2; 4 |
| TC-72-02 | идемпотентность | выполнен TC-72-01 | повторить тот же `POST` с тем же `Idempotency-Key` | 200, тот же `completion_id`; `SELECT count(*) = 1`; вторая запись не создана | 3.2 |
| TC-72-03 | негативный | материал не назначен участнику | `POST` по назначению другого участника | 404 `NOT_FOUND`; запись прохождения отсутствует; в журнале `access.denied` / `denied` | 3.2; 4 |
| TC-72-04 | негативный | версия материала — черновик | `POST` по назначению на черновик | 409 `STATE_CONFLICT`, сообщение о недоступности неопубликованной версии; запись не создана | 3.1, 3.2 |
| TC-72-05 | проверка версии | после TC-72-01 опубликована v2 | прочитать запись прохождения | `material_version_id` и `version_no` соответствуют v1; значения не перезаписаны | 3.2 |
| TC-72-06 | устойчивость | выполнен TC-72-01 | перезапуск контейнеров ядра и БД, повторное чтение | 200, запись и все отметки времени сохранены | 4; проверка 5 |
| TC-72-07 | негативный | назначение действует | `POST` с `confirmation_action` вне согласованного перечня | 422 `INVALID_VALUE` с указанием поля и допустимых значений; запись не создана | 3.2 |
| TC-72-08 | неполный результат | назначение действует | подтвердить прохождение с признаком неполноты | 409 либо 200 со `status=partial`, `is_complete=false`; статус участника не «выполнено» | 3.2 |

### 9. Что не входит

История обучения и статистика прохождения (7.2, 7.3), completion rate и показатели (7.19),
тесты знаний (7.4), уведомления участникам, корректирующее обучение (7.18), пересмотр
результата (7.20), массовые назначения.

## P22-73 — Результат 2: статус прохождения и норматив доступности назначения 5 минут

**Основание:** ТЗ CA_PS-2026-10, п. 3.2 и п. 8 (+ общее ТЗ, раздел 7.3)
**Модуль:** M2 · **Компонент:** core

### 1. Что реализовать

- Отображение статуса назначения и прохождения участнику (только свои) и уполномоченному
  оператору (в пределах области полномочий) — И-02, И-11.
- Модель статусов назначения: `created` → `available` → `in_progress` → `completed`; ветки
  `overdue`, `cancelled` (`docs/arch/02-domennaya-model.md`, п. 2.3).
- Набор отметок времени, достаточный для подтверждения норматива «назначение доступно не
  позднее 5 минут после публикации» (И-03), и эндпоинт выгрузки этих отметок для замера.
- Отражение `status = partial` как «не выполнено» (И-04).

### 2. Данные

| Поле | Тип | Обязательность | Правило заполнения |
|---|---|---|---|
| `assignment.status` | enum | да | вычисляется из отметок времени и состояния прохождения; хранится денормализованно |
| `material_version.published_at` | timestamptz | да | ставится при успешной публикации версии (P22-68); источник `t0` |
| `assignment.created_at` | timestamptz | да | момент создания назначения (P22-70) |
| `assignment.available_from` | timestamptz | да | момент, с которого назначение выдаётся участнику |
| `assignment.first_shown_at` | timestamptz | нет | первое успешное отображение назначения участнику по его запросу; источник `t1`; заполняется однократно |
| `assignment.started_at` | timestamptz | нет | первое открытие содержимого участником |
| `completion.occurred_at` | timestamptz | нет | время зафиксированного прохождения (P22-72) |
| `assignment.due_at` | timestamptz | нет | срок; при истечении статус `overdue` |
| `assignment.status_changed_at` | timestamptz | да | время последней смены статуса |

### 3. Интерфейс (API)

| Метод и путь | Назначение | Право | Коды ответов |
|---|---|---|---|
| `GET /api/my/assignments` | назначения и статусы участника | `training.read.own` | 200, 401, 403 |
| `GET /api/assignments?material_version_id&status&employee_id` | статусы группы для оператора | `training.read` | 200, 400, 401, 403 |
| `GET /api/assignments/{assignment_id}` | карточка назначения со статусом | `training.read` либо `training.read.own` | 200, 401, 403, 404 |
| `GET /api/assignments/{assignment_id}/timeline` | отметки времени для замера норматива | `training.read` | 200, 401, 403, 404 |
| `GET /api/materials/{material_id}/versions/{version_no}/availability` | сводка по норматив-замеру публикации | `training.read` | 200, 401, 403, 404 |

### 4. Правила и инварианты

1. Участник видит только свои назначения и результаты; результаты других участников недоступны (И-02).
2. Профиль чтения получает статусы без права изменения (мес. ТЗ п. 4, проверка 4 п. 8).
3. `status = completed` выставляется только при `completion.is_complete = true` (И-04).
4. `first_shown_at` заполняется однократно и не перезаписывается — иначе замер норматива непроверяем.
5. Все обращения к статусам персональных результатов журналируются (И-15).

### 5. Отметки времени и измерение норматива (норматив 5 минут)

- **Сохраняемые отметки:** `published_at`, `created_at`, `available_from`, `first_shown_at`,
  `started_at`, `completion.occurred_at`, `status_changed_at`.
- **Расчёт норматива** (по `docs/arch/06-ispytaniya-i-trassirovka.md`, п. 5): `t0` — отметка
  успешной публикации версии; `t1` — отметка первого успешного отображения назначения участнику
  по его запросу; норматив выполнен при `t1 − t0 ≤ 300 с`.
- **Точность и зона:** хранение — `timestamptz` в UTC, точность 1 мс; все компоненты, формирующие
  отметки, синхронизированы по NTP; отображение — Asia/Almaty.
- **Видимость проверяющему:** `GET /api/assignments/{id}/timeline` возвращает отметки и
  вычисленные `availability_latency_ms`, `norm_limit_ms = 300000`, `norm_met` (boolean); те же
  отметки присутствуют в журнале операций (`material.version.publish`, `assignment.view`), что
  даёт независимое подтверждение по п. 8 месячного ТЗ.
- **Условие действительности замера:** штатная работа интеграций и зафиксированные до замера
  параметры стенда и контрольные данные; при отказах в окне замера замер недействителен.
- **Требует согласования:** точка `t0` (публикация версии либо завершение создания назначения),
  критерий «штатной работы интеграций» и число успешных замеров — вопрос реестра 6.1 (P22-38, P22-81).

### 6. Зависимости и блокировки

- P22-68 (отметка публикации), P22-70 (создание назначения), P22-71 (показ назначения в портале),
  P22-72 (отметка прохождения), P22-74 (права), P22-76 (журнал как источник отметок).
- Открытый вопрос 6.1 — до его закрытия замер фиксируется по варианту «`t0` = публикация версии».
- Синхронизация времени компонентов стенда (вопрос 2.15) — условие проверяемости.

### 7. Определение готовности (DoD)

Кейсы TC-73-01…TC-73-07 пройдены; `timeline` возвращает полный набор отметок; на стенде выполнен
замер норматива с результатом `norm_met = true`; протокол замера приложен к P22-81; статусы
отображаются участнику и оператору с разграничением по И-02 и И-11.

### 8. Тест-кейсы

| ID | Тип | Предусловие | Шаги | Ожидаемый результат | Пункт ТЗ |
|---|---|---|---|---|---|
| TC-73-01 | норматив | материал в черновике, группа подготовлена | опубликовать версию, запросить `GET /api/my/assignments` участником, снять `timeline` | `t1 − t0 ≤ 300000 мс`, `norm_met=true`; отметки `published_at` и `first_shown_at` непустые и совпадают с журналом | 3.2; 8 |
| TC-73-02 | позитивный | назначение доступно | участник запрашивает свои назначения | 200; статус `available`; состав полей без данных других участников | 3.2 |
| TC-73-03 | негативный | участник вне группы | тот же запрос неназначенным участником | 200 с пустым перечнем либо 403; назначение и результаты других участников не возвращаются; в журнале `assignment.view` / `denied` при отказе | 3.2; 4 |
| TC-73-04 | позитивный | прохождение зафиксировано (TC-72-01) | оператор запрашивает `GET /api/assignments?material_version_id=...` | 200; статус `completed`, `occurred_at` соответствует записи `completion` | 3.2 |
| TC-73-05 | негативный | зафиксирован `status=partial` | запросить статус участником и оператором | статус не `completed` (`in_progress`/`partial`); признак успешности отсутствует | 3.2 |
| TC-73-06 | устойчивость | выполнены TC-73-01, TC-73-04 | перезапуск ядра и БД, повторный запрос `timeline` | все отметки времени сохранены без изменения значений; `norm_met` воспроизводится | 4; проверка 5 |
| TC-73-07 | негативный | назначение существует | `GET /api/assignments/{id}/timeline` профилем чтения и анонимно | профиль чтения — 200 без права изменения; анонимный запрос — 401; оба обращения в журнале | 4; проверка 4 |

### 9. Что не входит

Уведомления о назначении, периодическое и обязательное назначение по расписанию (7.3, M15),
расчёт completion rate и baseline (7.19), промышленное подтверждение норматива при реальных
интеграциях, нагрузочное подтверждение норматива (раздел 13).

## P22-76 — Журнал операций: пользователь, время, объект, операция, результат

**Основание:** ТЗ CA_PS-2026-10, п. 4 (+ общее ТЗ, раздел 9; раздел 10 — защита журнала)
**Модуль:** M12 · **Компонент:** core

### 1. Что реализовать

- Запись в неизменяемый журнал (append-only) по каждой прикладной операции сценария с
  обязательными атрибутами: пользователь, время, объект, операция, результат (мес. ТЗ п. 4).
- Журналирование **и успешных операций, и отказов** (в доступе, по валидации, по состоянию).
- Поиск, фильтрацию, экспорт, контроль целостности и разграничение доступа к журналу
  (раздел 9; `docs/arch/04-bezopasnost-i-privacy.md`, п. 5.3).
- Техническую невозможность изменения и удаления записей прикладным пользователем: отсутствие
  методов изменения в API, отсутствие прав `UPDATE`/`DELETE` у прикладной роли БД, цепочка
  контрольных сумм записей.
- Фильтр исключения секретов: пароли, ключи, токены и значения форм в журнал не попадают (И-09).

### 2. Данные

Обязательные атрибуты записи `audit_event` (append-only):

| Поле | Тип | Обязательность | Правило заполнения |
|---|---|---|---|
| `audit_event_id` | uuid | да | генерируется платформой; первичный ключ |
| `seq_no` | bigserial | да | монотонная последовательность, основа цепочки целостности |
| `occurred_at` | timestamptz | да | время операции, UTC, точность 1 мс |
| `recorded_at` | timestamptz | да | время записи в журнал |
| `actor_type` | enum(`user`,`service`,`anonymous`) | да | субъект операции |
| `actor_id` / `actor_login` | uuid / varchar | да для `user`,`service` | учётная запись или техническая УЗ; для анонимного запроса — `anonymous` |
| `session_id` | uuid | нет | идентификатор сессии, если есть |
| `source_ip` | inet | да | адрес источника запроса |
| `object_type` | enum(`material`,`material_version`,`assignment`,`completion`,`access_profile`,`audit`) | да | тип объекта операции |
| `object_id` | uuid | да | идентификатор объекта; при отказе до разрешения объекта — запрошенный идентификатор |
| `object_version` | varchar | нет | версия материала, если применимо |
| `operation` | varchar(64) | да | код операции из перечня ниже |
| `result` | enum(`success`,`denied`,`error`) | да | исход операции |
| `reason_code` | varchar(48) | да при `denied`/`error` | код класса ошибки (P22-79) |
| `old_value` / `new_value` | jsonb | да для операций изменения | предыдущее и новое значения атрибута и основание изменения (раздел 9) |
| `operation_id` | uuid | да | ключ идемпотентности записи; `UNIQUE` |
| `prev_hash` / `record_hash` | bytea | да | `record_hash = H(prev_hash ‖ канонизированная запись)` |

Перечень журналируемых операций сценария: `material.create`, `material.version.create`,
`material.version.publish`, `material.version.reopen`, `assignment.create`, `assignment.view`,
`completion.record`, `completion.view`, `access_profile.change`, `auth.login`, `auth.failed`,
`access.denied`, `audit.search`, `audit.export`, `audit.integrity_check`, `component.error`.

### 3. Интерфейс (API)

| Метод и путь | Назначение | Право | Коды ответов |
|---|---|---|---|
| `GET /api/audit?from&to&actor&object_type&object_id&operation&result&page` | поиск и фильтрация записей | `audit.read` | 200, 400, 401, 403 |

### 4. Правила и инварианты

1. И-15: каждая прикладная операция сценария даёт ровно одну запись журнала (ключ `operation_id`).
2. Ни одна роль не имеет операций изменения и удаления по журналу: методы отсутствуют в API,
   прикладная роль БД имеет только `INSERT`/`SELECT`, таблица защищена триггером запрета
   `UPDATE`/`DELETE` (раздел 9; `04-bezopasnost-i-privacy.md`, п. 1.2, инвариант 1).
3. Разграничение доступа: доступ к журналу — только роли с `audit.read`; профиль чтения получает
   ограниченный состав полей; работник-участник доступа к журналу не имеет; обращения к журналу
   сами журналируются (`audit.search`, `audit.export`).
4. Запись не содержит паролей, ключей, токенов и значений, введённых в формы: применяется
   allowlist полей и фильтр заголовков `Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`.
5. Контроль целостности: разрыв цепочки хешей выявляется и возвращается в `GET /api/audit/integrity`
   с указанием `seq_no` первой несогласованной записи.
6. Отказ записи в журнал трактуется как отказ операции (fail-closed), событие буферизуется и не
   теряется (см. P22-79, `STORAGE_UNAVAILABLE`).

### 5. Отметки времени и измерение норматива

Запись хранит `occurred_at` и `recorded_at`; журнал является источником отметок `t0`/`t1` для
замера норматива 5 минут (P22-73) и базой для норматива 60 секунд в полном объёме (раздел 9,
P22-97 — вне октябрьского объёма).

### 6. Зависимости и блокировки

- P22-74 (аутентификация и профили) — источник `actor_*` и решения о доступе.
- P22-66 (схема данных), P22-77 (контейнеризация, отделение данных от приложения), P22-78 (бэкап).
- P22-88 — расширение до полного перечня событий раздела 9; P22-79 — коды и классы ошибок.
- Открытые вопросы: 5.3 (сроки хранения журналов), 2.16 (состав и формат передачи журналов наружу),
  6.3 (перечень критичных результатов) — на октябрьский объём не блокирующие.

### 7. Определение готовности (DoD)

Кейсы TC-76-01…TC-76-08 пройдены; все операции перечня п. 2 журналируются с результатом;
попытка изменения записи через API и через прикладное подключение к БД отклоняется и фиксируется;
`GET /api/audit/integrity` подтверждает целостность; отчёт отрицательного поиска контрольного
значения по журналу, экспорту и резервной копии приложен к P22-80.

## P22-79 — Обработка ошибок: понятные сообщения и признак неполного результата

**Основание:** ТЗ CA_PS-2026-10, п. 3.2 (+ п. 4 — фиксация отказов в журнале)
**Модуль:** M2/M12 (сквозное решение ядра) · **Компонент:** core

### 1. Что реализовать

- Единый конверт ошибки для всех эндпоинтов сценария, одинаковый для `web-admin` и `web-portal`.
- Классификацию ошибок на четыре класса: валидация, право, конфликт состояния, недоступность
  хранилища — с кодом, сообщением пользователю и записью в журнал.
- Признак неполного результата: неполный результат не отображается и не возвращается как
  успешный (И-04).
- Понятные сообщения для оператора и участника: указание поля, причины и допустимых значений
  без технических трассировок и без раскрытия внутреннего устройства.
- Фиксацию каждого отказа в журнале M12 (`result = denied` либо `error`) с `reason_code`.

### 2. Данные

Конверт ошибки (HTTP body):

| Поле | Тип | Обязательность | Правило заполнения |
|---|---|---|---|
| `code` | varchar(48) | да | машинный код класса ошибки из таблицы п. 4 |
| `message` | text | да | текст для пользователя на русском, без трассировок и секретов |
| `field` | varchar(64) | да для валидации | имя отклонённого поля |
| `allowed` | array | нет | допустимые значения согласованного формата |
| `operation_id` | uuid | да | совпадает с `audit_event.operation_id` — связь ответа и записи журнала |
| `retry_after_sec` | int | да для 503 | интервал повторной попытки |

Классы ошибок:

| Класс | Код | HTTP | Сообщение пользователю | Запись в журнале |
|---|---|---|---|---|
| Валидация формата или значения | `INVALID_VALUE` / `VALIDATION_FAILED` | 422 / 400 | «Значение поля «{field}» не соответствует согласованному формату. Допустимые значения: {allowed}.» | `result=error`, `reason_code=INVALID_VALUE`, `field` без значения ввода |
| Отсутствие аутентификации | `UNAUTHENTICATED` | 401 | «Для выполнения операции требуется вход в систему.» | `result=denied`, `actor_type=anonymous` |
| Отсутствие права | `ACCESS_DENIED` | 403 | «У вашего профиля нет права на эту операцию. Обратитесь к ответственному оператору.» | `result=denied`, `operation=access.denied` |
| Объект вне области доступа | `NOT_FOUND` | 404 | «Объект не найден или недоступен.» | `result=denied`, без раскрытия существования объекта |
| Конфликт состояния | `STATE_CONFLICT` | 409 | «Операция недопустима в текущем состоянии объекта: {состояние}.» | `result=error`, `old_value` = состояние объекта |
| Повтор с другим телом | `IDEMPOTENCY_CONFLICT` | 409 | «Повторный запрос с тем же ключом содержит другие данные.» | `result=error` |
| Неполный результат | `INCOMPLETE_RESULT` | 409 | «Результат неполный и не может быть зафиксирован как успешный: {что не выполнено}.» | `result=error`, `new_value.status=partial` |
| Недоступность хранилища | `STORAGE_UNAVAILABLE` | 503 | «Сервис временно недоступен, данные не сохранены. Повторите попытку через {retry_after_sec} с.» | `result=error`; запись буферизуется локально и досылается в журнал после восстановления |

### 3. Интерфейс (API)

| Метод и путь | Назначение | Право | Коды ответов |
|---|---|---|---|
| все эндпоинты P22-72, P22-73, P22-76 и эндпоинты M1/M11 сценария | единый конверт ошибки вместо произвольных текстов | по праву целевой операции | 400, 401, 403, 404, 409, 422, 503 |
| `POST /api/my/assignments/{id}/completion` | возврат `INCOMPLETE_RESULT` при неполном подтверждении | `training.complete.own` | 409 |
| `GET /api/health`, `GET /api/health/ready` | диагностика состояния компонентов и доступности хранилищ | без прикладного права, только внутренний контур | 200, 503 |

### 4. Правила и инварианты

1. И-04: при любом неполном результате ответ не имеет признака успеха, статус назначения не
   переходит в `completed`, в журнале фиксируется `status=partial`.
2. Сообщение не содержит стек-трейсов, SQL, внутренних путей, имён хостов, паролей, ключей и
   токенов (И-09; мес. ТЗ п. 4).
3. Разделение `403` и `404`: при обращении к объекту вне области доступа возвращается `404`,
   чтобы не раскрывать существование объекта; в журнале фиксируется именно отказ в доступе.
4. При недоступности хранилища операция не подтверждается: изменение не сохраняется частично,
   транзакция откатывается целиком, событие журнала не теряется.
5. Каждый отказ сопровождается записью журнала; `operation_id` в ответе позволяет проверяющему
   найти запись (связка «ответ API ↔ запись журнала»).
6. Один и тот же класс ошибки даёт одинаковый `code` во всех эндпоинтах.

### 5. Отметки времени и измерение норматива

Запись об отказе содержит `occurred_at` и `recorded_at`; отказы в окне замера норматива 5 минут
фиксируются и делают замер недействительным (условие штатной работы, P22-73, п. 5).

### 6. Зависимости и блокировки

- P22-74 (решения о праве и аутентификации), P22-76 (журнал как приёмник отказов),
  P22-72, P22-73 (операции-источники), P22-78 (диагностика и контроль состояния).
- Вопрос реестра 7.3 — согласованные форматы и допустимые значения контрольных данных;
  без него перечень сообщений валидации не финализируется.

### 7. Определение готовности (DoD)

Кейсы TC-79-01…TC-79-08 пройдены; все восемь классов ошибок воспроизведены на стенде с
ожидаемым `code`, сообщением и записью журнала; не остаётся эндпоинтов, возвращающих
необработанную ошибку (500 без конверта); проверено отсутствие секретов и трассировок в
сообщениях; результаты переданы в P22-81.

раздела 9 (P22-88), мониторинг и алертинг (P22-78), ретраи интеграций (8.1).
