Опора: месячное ТЗ `docs/source/tz-ca_ps-2026-10.txt`; сущности, состояния и инварианты И-01…И-16 — `docs/arch/02-domennaya-model.md`; границы модулей, события и внешний API — `docs/arch/01-moduli-i-granicy.md`; права и аудит — `docs/arch/04-bezopasnost-i-privacy.md` (пп. 1.2, 5); методика замера нормативов — `docs/arch/06-ispytaniya-i-trassirovka.md` (п. 5); открытые вопросы — `docs/05-otkrytye-voprosy.md`.

## P22-72 — Результат 2: фиксация прохождения — материал, версия, участник, время

**Основание:** ТЗ CA_PS-2026-10, п. 3.2, п. 4 (+ общее ТЗ, раздел 7.3)
**Модуль:** M2 · **Компонент:** core

### 1. Что реализовать

- Идемпотентную фиксацию прохождения согласованным действием участника: вызов подтверждения создаёт одну неизменяемую запись `completion` (И-16), повторный вызов второй записи не создаёт.
- Сохранение идентификатора материала, **номера версии материала**, участника и времени действия (п. 3.2).
- Проверку предусловий приложением: назначение существует, принадлежит вызывающему участнику, ссылается на опубликованную версию, не отменено и не просрочено (И-01, И-02, И-11).
- Признак полноты: неполное подтверждение сохраняется как `partial` и не обозначается успешным (И-04).
- Публикацию события `training.completed` (M7, M12), запись операции в журнал (И-15) и хранение в Postgres вне образа: перезапуск не приводит к потере данных (п. 4, проверка 5 п. 8).

### 2. Данные

Таблица `completion` (append-only):

| Поле | Тип | Обязательность | Правило заполнения |
|---|---|---|---|
| `completion_id` | uuid | да | генерируется платформой, первичный ключ |
| `assignment_id` | uuid | да | ссылка на `assignment` вызывающего участника |
| `employee_id` | uuid | да | берётся из назначения, не из тела запроса (защита от подмены) |
| `material_id` | uuid | да | копируется из назначения |
| `material_version_id` | uuid | да | конкретная опубликованная версия, на которую выдано назначение |
| `version_no` | int | да | номер версии на момент фиксации, исторически не перезаписывается |
| `occurred_at`, `recorded_at` | timestamptz | да | время действия участника и время сохранения записи, проставляет сервер |
| `status` | enum(`completed`,`partial`) | да | `partial` при неполном результате (И-04) |
| `is_complete` | boolean | да | `true` только при `status = completed` |
| `confirmation_action` | enum(`explicit_confirm`) | да | согласованное действие, иные значения отклоняются |
| `idempotency_key` | varchar(64) | да | из заголовка запроса |
| `operation_id` | uuid | да | ключ связи с записью журнала M12, возвращается в ответе API |

Ограничения: `UNIQUE (assignment_id) WHERE status='completed'`; `UNIQUE (assignment_id, idempotency_key)`; прикладная роль БД без прав `UPDATE`/`DELETE` (корректировка — только пересмотром результата, 7.20).

### 3. Интерфейс (API)

| Метод и путь | Назначение | Право | Коды ответов |
|---|---|---|---|
| `POST /api/my/assignments/{assignment_id}/completion` | фиксация прохождения участником | `training.complete.own` | 201, 200 (повтор), 400, 401, 403, 404, 409, 422, 503 |
| `GET /api/my/assignments/{assignment_id}/completion` | собственная запись прохождения | `training.read.own` | 200, 401, 403, 404 |
| `GET /api/completions?employee_id&material_id&material_version_id` | факты прохождения для оператора и профиля чтения | `training.read` | 200, 400, 401, 403 |

### 4. Правила и инварианты

1. И-01: прохождение по версии «черновик» невозможно — 409 `STATE_CONFLICT`.
2. И-02: по чужому либо неназначенному материалу — 404 `NOT_FOUND`, без раскрытия существования объекта.
3. Повтор идемпотентен: второй вызов — 200 и тот же `completion_id`; тот же ключ с другим телом — 409 `IDEMPOTENCY_CONFLICT`.
4. Фиксируется версия, а не только материал: публикация новой версии после фиксации не меняет `material_version_id` и `version_no` сохранённой записи.
5. И-16: завершённая запись неизменяема, методов изменения и удаления в API нет.
6. Фиксация и запись журнала выполняются в одной транзакции; при недоступности журнала операция не подтверждается успешной (P22-79, `STORAGE_UNAVAILABLE`).
7. Секреты и значения форм не сохраняются и не логируются (И-09).

### 5. Отметки времени и измерение норматива

Сохраняются `occurred_at` и `recorded_at`; `occurred_at` — источник `completed_at` события `training.completed` и значение `t1` в замерах P22-73. Собственного норматива у задачи нет.

### 6. Зависимости и блокировки

P22-66 (схема данных), P22-68 (публикация версии), P22-70 (назначение группе) — предусловия; P22-74 — решение о праве; P22-76 — журнал; P22-79 — контракт ошибок; вопрос реестра 7.3 — контрольные данные и допустимые значения.

### 7. Определение готовности (DoD)

Кейсы TC-72-01…TC-72-08 пройдены на стенде; запись читается после перезапуска и после восстановления из копии (проверка 5 п. 8); событие `training.completed` публикуется один раз на прохождение; в журнале есть запись операции с результатом; миграции и индексы включены в поставку.

### 8. Тест-кейсы

| ID | Тип | Предусловие | Шаги | Ожидаемый результат | Пункт ТЗ |
|---|---|---|---|---|---|
| TC-72-01 | позитивный | опубликована версия v1, участник назначен | `POST .../completion` | 201; в `completion` одна строка: `material_version_id` v1, `version_no=1`, `status=completed`; в журнале `completion.record` / `success` | 3.2; 4 |
| TC-72-02 | идемпотентность | выполнен TC-72-01 | повторить тот же `POST` с тем же `Idempotency-Key` | 200 и тот же `completion_id`; `count(*)=1` — вторая запись не создана | 3.2 |
| TC-72-03 | негативный | материал участнику не назначен | `POST` по назначению другого участника | 404 `NOT_FOUND`; запись отсутствует; в журнале `access.denied` / `denied` | 3.2; 4 |
| TC-72-04 | негативный | версия материала — черновик | `POST` по назначению на черновик | 409 `STATE_CONFLICT` с сообщением о неопубликованной версии; запись не создана | 3.1, 3.2 |
| TC-72-05 | фиксация версии | после TC-72-01 опубликована v2 | прочитать запись прохождения | `material_version_id` и `version_no` соответствуют v1, значения не перезаписаны | 3.2 |
| TC-72-06 | устойчивость | выполнен TC-72-01 | перезапуск ядра и БД, повторное чтение | 200; запись и отметки времени сохранены без изменений | 4; проверка 5 |
| TC-72-07 | валидация | назначение действует | `POST` с `confirmation_action` вне согласованного перечня | 422 `INVALID_VALUE` с полем и допустимыми значениями; запись не создана | 3.2 |
| TC-72-08 | неполный результат | назначение действует | подтвердить прохождение с незавершённым обязательным шагом | 409 `INCOMPLETE_RESULT` либо `status=partial` с `is_complete=false`; статус не «выполнено» | 3.2 |

### 9. Что не входит

История обучения и статистика (7.2, 7.3), completion rate и baseline (7.19), тесты знаний (7.4), уведомления, корректирующее обучение (7.18), пересмотр результата (7.20), массовые назначения.

## P22-73 — Результат 2: статус прохождения и норматив доступности назначения 5 минут

**Основание:** ТЗ CA_PS-2026-10, п. 3.2, п. 8 (+ общее ТЗ, раздел 7.3)
**Модуль:** M2 · **Компонент:** core

### 1. Что реализовать

- Показ статуса назначения и прохождения участнику (только свои) и уполномоченному оператору в пределах его области (И-02, И-11); профиль чтения — просмотр без изменения.
- Статусы назначения `created` → `available` → `in_progress` → `completed`, ветки `overdue` и `cancelled` (доменная модель, п. 2.3); `partial` отображается как «не выполнено» (И-04).
- Набор отметок времени, достаточный для подтверждения норматива «доступность назначения не позднее 5 минут после публикации» (И-03), и эндпоинт их выгрузки для замера.

### 2. Данные

| Поле | Тип | Обязательность | Правило заполнения |
|---|---|---|---|
| `assignment.status` | enum | да | вычисляется из отметок времени и состояния прохождения, хранится денормализованно |
| `material_version.published_at` | timestamptz | да | отметка успешной публикации версии (P22-68), источник `t0` |
| `assignment.created_at` | timestamptz | да | момент создания назначения (P22-70) |
| `assignment.available_from` | timestamptz | да | момент, с которого назначение выдаётся участнику |
| `assignment.first_shown_at` | timestamptz | нет | первое успешное отображение назначения участнику, источник `t1`, заполняется однократно |
| `assignment.started_at` | timestamptz | нет | первое открытие содержимого участником |
| `completion.occurred_at` | timestamptz | нет | время зафиксированного прохождения (P22-72) |
| `assignment.due_at`, `assignment.status_changed_at` | timestamptz | `due_at` — нет, `status_changed_at` — да | срок (при истечении статус `overdue`) и время последней смены статуса |

### 3. Интерфейс (API)

| Метод и путь | Назначение | Право | Коды ответов |
|---|---|---|---|
| `GET /api/my/assignments` | назначения и статусы участника | `training.read.own` | 200, 401, 403 |
| `GET /api/assignments?material_version_id&status&employee_id` | статусы группы для оператора | `training.read` | 200, 400, 401, 403 |
| `GET /api/assignments/{assignment_id}` | карточка назначения со статусом | `training.read` либо `training.read.own` | 200, 401, 403, 404 |
| `GET /api/assignments/{assignment_id}/timeline` | отметки времени и результат замера норматива | `training.read` | 200, 401, 403, 404 |

### 4. Правила и инварианты

1. Участник видит только свои назначения и результаты (И-02); профиль чтения не изменяет данные и настройки (п. 4, проверка 4 п. 8).
2. `status=completed` выставляется только при `completion.is_complete=true` (И-04).
3. `first_shown_at` заполняется однократно и не перезаписывается — иначе замер норматива непроверяем.
4. Обращения к статусам персональных результатов журналируются (И-15).

### 5. Отметки времени и измерение норматива (норматив 5 минут)

- **Сохраняемые отметки:** `published_at`, `created_at`, `available_from`, `first_shown_at`, `started_at`, `completion.occurred_at`, `status_changed_at`.
- **Расчёт** (методика `docs/arch/06-ispytaniya-i-trassirovka.md`, п. 5): `t0` — отметка успешной публикации версии, `t1` — отметка первого успешного отображения назначения участнику по его запросу; норматив выполнен при `t1 − t0 ≤ 300 000 мс`.
- **Точность и часовой пояс:** хранение в UTC с точностью 1 мс, компоненты, формирующие отметки, синхронизированы по NTP; проверяющему значения показываются в Asia/Almaty (UTC+5).
- **Видимость проверяющему:** `GET /api/assignments/{id}/timeline` возвращает отметки, `availability_latency_ms`, `norm_limit_ms=300000` и `norm_met`; те же отметки есть в журнале (`material.version.publish`, `assignment.view`), что даёт независимое подтверждение по п. 8.
- **Условия действительности замера:** штатная работа интеграций; параметры стенда и контрольные данные зафиксированы до замера; при зарегистрированных в окне замера отказах замер недействителен.
- **Требует согласования:** точка `t0`, критерий «штатной работы интеграций», число успешных замеров — вопрос реестра 6.1 (P22-38, P22-81).

### 6. Зависимости и блокировки

P22-68 (отметка публикации), P22-70 (создание назначения), P22-71 (показ в портале), P22-72 (отметка прохождения), P22-74 (права), P22-76 (журнал как независимый источник отметок); вопрос 6.1 — точка отсчёта норматива; вопрос 2.15 — синхронизация времени компонентов стенда.

### 7. Определение готовности (DoD)

Кейсы TC-73-01…TC-73-07 пройдены; `timeline` возвращает полный набор отметок; на стенде выполнен замер с результатом `norm_met=true` и протоколом для P22-81; разграничение по И-02 и И-11 подтверждено.

### 8. Тест-кейсы

| ID | Тип | Предусловие | Шаги | Ожидаемый результат | Пункт ТЗ |
|---|---|---|---|---|---|
| TC-73-01 | норматив | материал в черновике, группа подготовлена | опубликовать версию, запросить `GET /api/my/assignments` участником, снять `timeline` | `t1 − t0 ≤ 300 000 мс`, `norm_met=true`; `published_at` и `first_shown_at` непусты и совпадают с записями журнала | 3.2; 8 |
| TC-73-02 | позитивный | назначение доступно | участник запрашивает свои назначения | 200, статус `available`; данные других участников отсутствуют | 3.2 |
| TC-73-03 | негативный | участник вне назначенной группы | тот же запрос неназначенным участником | пустой перечень либо 403; назначение и чужие результаты не возвращаются; отказ зафиксирован в журнале | 3.2; 4 |
| TC-73-04 | позитивный | выполнен TC-72-01 | оператор запрашивает `GET /api/assignments?material_version_id=...` | 200, статус `completed`, `occurred_at` совпадает с записью `completion` | 3.2 |
| TC-73-05 | неполный результат | зафиксирован `status=partial` | запросить статус участником и оператором | статус не `completed`, признак успешности отсутствует | 3.2 |
| TC-73-06 | устойчивость | выполнены TC-73-01 и TC-73-04 | перезапуск ядра и БД, повторный запрос `timeline` | отметки времени сохранены без изменения значений, `norm_met` воспроизводится | 4; проверка 5 |
| TC-73-07 | доступ | назначение существует | `GET .../timeline` профилем чтения и анонимно | профиль чтения — 200 без права изменения; анонимно — 401; оба обращения в журнале | 4; проверка 4 |

### 9. Что не входит

Уведомления, периодические и обязательные назначения по расписанию (7.3, M15), completion rate и baseline (7.19), подтверждение норматива при промышленных интеграциях и под нагрузкой (раздел 13).

## P22-76 — Журнал операций: пользователь, время, объект, операция, результат

**Основание:** ТЗ CA_PS-2026-10, п. 4 (+ общее ТЗ, раздел 9; раздел 10 — защита журнала)
**Модуль:** M12 · **Компонент:** core

### 1. Что реализовать

- Запись в неизменяемый журнал (append-only) по каждой операции сценария: пользователь, время, объект, операция, результат (п. 4); фиксируются **и успешные операции, и отказы** (в доступе, по валидации, по состоянию).
- Поиск, фильтрацию, экспорт, контроль целостности и разграничение доступа к журналу (раздел 9; ИБ-приложение, п. 5.3).
- Защиту от изменения прикладным пользователем: отсутствие методов изменения в API, отсутствие прав `UPDATE`/`DELETE` у прикладной роли БД, триггер запрета, цепочка контрольных сумм записей.
- Фильтр исключения секретов: пароли, ключи, токены и значения форм в журнал не попадают (И-09).

### 2. Данные

Обязательные атрибуты записи `audit_event`:

| Поле | Тип | Обязательность | Правило заполнения |
|---|---|---|---|
| `audit_event_id`, `seq_no` | uuid, bigserial | да | идентификатор записи и монотонная последовательность — основа цепочки целостности |
| `occurred_at`, `recorded_at` | timestamptz | да | время операции и время записи, UTC, точность 1 мс |
| `actor_type` | enum(`user`,`service`,`anonymous`) | да | субъект операции |
| `actor_id`, `actor_login` | uuid, varchar | да для `user` и `service` | учётная либо техническая запись; для анонимного запроса — `anonymous` |
| `session_id`, `source_ip` | uuid, inet | `source_ip` — да | сессия (если есть) и адрес источника запроса |
| `object_type` | enum(`material`,`material_version`,`assignment`,`completion`,`access_profile`,`audit`) | да | тип объекта операции |
| `object_id`, `object_version` | uuid, varchar | `object_id` — да | объект операции (при отказе — запрошенный идентификатор) и версия материала, если применимо |
| `operation` | varchar(64) | да | код операции из перечня ниже |
| `result` | enum(`success`,`denied`,`error`) | да | исход операции |
| `reason_code` | varchar(48) | да при `denied` и `error` | код класса ошибки (P22-79) |
| `old_value`, `new_value` | jsonb | да для операций изменения | предыдущее и новое значение атрибута и основание изменения (раздел 9) |
| `operation_id` | uuid | да | ключ идемпотентности записи, `UNIQUE`; возвращается в ответе API |
| `prev_hash`, `record_hash` | bytea | да | `record_hash = H(prev_hash ‖ канонизированная запись)` |

Журналируемые операции сценария: `material.create`, `material.version.create`, `material.version.publish`, `material.version.reopen`, `assignment.create`, `assignment.view`, `completion.record`, `completion.view`, `access_profile.change`, `auth.login`, `auth.failed`, `access.denied`, `audit.search`, `audit.export`, `audit.integrity_check`, `component.error`.

### 3. Интерфейс (API)

| Метод и путь | Назначение | Право | Коды ответов |
|---|---|---|---|
| `GET /api/audit?from&to&actor&object_type&object_id&operation&result&page` | поиск и фильтрация записей | `audit.read` | 200, 400, 401, 403 |
| `GET /api/audit/{audit_event_id}` | просмотр записи | `audit.read` | 200, 401, 403, 404 |
| `POST /api/audit/export` | экспорт выборки в согласованном формате (JSONL/CSV) | `audit.export` | 202, 400, 401, 403 |
| `GET /api/audit/integrity?from&to` | контроль целостности цепочки записей | `audit.read` | 200, 401, 403 |
| `PUT`/`PATCH`/`DELETE /api/audit/{id}` | **не реализуются** | — | 405 для любой роли |

### 4. Правила и инварианты

1. И-15: каждая прикладная операция сценария даёт ровно одну запись журнала (ключ `operation_id`).
2. **Защита от изменения:** ни одна роль не имеет операций изменения и удаления по журналу — методы отсутствуют в API, прикладная роль БД имеет только `INSERT`/`SELECT`, таблица защищена триггером запрета `UPDATE`/`DELETE` (раздел 9; ИБ-приложение, п. 1.2, инвариант 1).
3. **Разграничение доступа:** чтение и экспорт — только роли с `audit.read` и `audit.export`; профиль чтения — ограниченный состав полей без `old_value`/`new_value`; работник-участник доступа к журналу не имеет; обращения к журналу журналируются (`audit.search`, `audit.export`).
4. Запись не содержит паролей, ключей, токенов и значений форм: allowlist полей плюс фильтр заголовков `Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`; тела запросов не логируются.
5. Контроль целостности: разрыв цепочки выявляется, `GET /api/audit/integrity` возвращает `seq_no` первой несогласованной записи.
6. Отказ записи в журнал трактуется как отказ операции (fail-closed); событие буферизуется локально и досылается, то есть не теряется (P22-79, `STORAGE_UNAVAILABLE`).

### 5. Отметки времени и измерение норматива

Запись хранит `occurred_at` и `recorded_at`; журнал — независимый источник отметок `t0`/`t1` для норматива 5 минут (P22-73) и база для норматива 60 секунд в полном объёме (раздел 9, P22-97 — вне октябрьского объёма).

### 6. Зависимости и блокировки

P22-74 (источник `actor_*` и решения о доступе), P22-66 (схема данных), P22-77 (отделение данных от приложения), P22-78 (резервное копирование журнала), P22-88 (расширение до полного перечня раздела 9), P22-79 (коды ошибок); вопросы реестра 5.3 (сроки хранения), 2.16 (состав и формат передачи наружу), 6.3 (перечень критичных результатов).

### 7. Определение готовности (DoD)

Кейсы TC-76-01…TC-76-08 пройдены; все операции перечня п. 2 журналируются с результатом; попытки изменения записи через API и через прикладное подключение к БД отклоняются и фиксируются; `GET /api/audit/integrity` подтверждает целостность; отчёт отрицательного поиска контрольных значений по журналу, экспорту и резервной копии передан в P22-80.

## P22-79 — Обработка ошибок: понятные сообщения и признак неполного результата

**Основание:** ТЗ CA_PS-2026-10, п. 3.2, п. 4 (+ общее ТЗ, разделы 9, 10)
**Модуль:** M2/M12 — сквозное решение ядра · **Компонент:** core

### 1. Что реализовать

- Единый конверт ошибки для всех эндпоинтов сценария, одинаковый для `web-admin` и `web-portal`; необработанных ответов 500 без конверта не остаётся.
- Классы ошибок (валидация, право, конфликт состояния, недоступность хранилища) с кодом, сообщением пользователю и записью в журнал — таблица п. 2.
- Признак неполного результата: неполный результат не возвращается и не отображается как успешный (И-04).
- Понятные сообщения оператору и участнику — поле, причина, допустимые значения, без трассировок, SQL, внутренних путей и секретов; фиксация каждого отказа в журнале M12 (`result = denied` либо `error`) с `reason_code`.

### 2. Данные

Конверт ошибки: `code` (varchar(48), обязателен, машинный код класса), `message` (text, обязателен, текст пользователю на русском без трассировок и секретов), `field` (varchar(64), обязателен для валидации, имя отклонённого поля), `allowed` (array, необязателен, допустимые значения согласованного формата), `operation_id` (uuid, обязателен, совпадает с `audit_event.operation_id` — связь ответа и записи журнала), `retry_after_sec` (int, обязателен для 503, интервал повторной попытки).

| Класс ошибки | Код | HTTP | Сообщение пользователю | Запись в журнале |
|---|---|---|---|---|
| Валидация значения или запроса | `INVALID_VALUE`, `VALIDATION_FAILED` | 422, 400 | «Значение поля «{field}» не соответствует согласованному формату. Допустимые значения: {allowed}.» | `result=error`, `reason_code` = код класса, поле указано без значения ввода |
| Нет аутентификации | `UNAUTHENTICATED` | 401 | «Для выполнения операции требуется вход в систему.» | `result=denied`, `actor_type=anonymous`, `operation=auth.failed` |
| Нет права | `ACCESS_DENIED` | 403 | «У вашего профиля нет права на эту операцию. Обратитесь к ответственному оператору.» | `result=denied`, `operation=access.denied` |
| Объект вне области доступа | `NOT_FOUND` | 404 | «Объект не найден или недоступен.» | `result=denied`, без раскрытия существования объекта |
| Конфликт состояния | `STATE_CONFLICT` | 409 | «Операция недопустима в текущем состоянии объекта: {состояние}.» | `result=error`, `old_value` = состояние объекта |
| Повтор с другим телом | `IDEMPOTENCY_CONFLICT` | 409 | «Повторный запрос с тем же ключом содержит другие данные.» | `result=error` |
| Неполный результат | `INCOMPLETE_RESULT` | 409 | «Результат неполный и не может быть зафиксирован как успешный: {что не выполнено}.» | `result=error`, `new_value.status=partial` |
| Недоступность хранилища | `STORAGE_UNAVAILABLE` | 503 | «Сервис временно недоступен, данные не сохранены. Повторите попытку через {retry_after_sec} с.» | `result=error`; запись буферизуется и досылается после восстановления |

### 3. Интерфейс (API)

| Метод и путь | Назначение | Право | Коды ответов |
|---|---|---|---|
| все эндпоинты P22-72, P22-73, P22-76 и эндпоинты M1/M11 сценария | единый конверт ошибки вместо произвольных текстов | право целевой операции | 400, 401, 403, 404, 409, 422, 503 |
| `POST /api/my/assignments/{id}/completion` | возврат `INCOMPLETE_RESULT` при неполном подтверждении | `training.complete.own` | 409 |
| `GET /api/health`, `GET /api/health/ready` | диагностика состояния компонентов и доступности хранилищ | внутренний контур | 200, 503 |

### 4. Правила и инварианты

1. И-04: при неполном результате ответ не содержит признака успеха, статус назначения не переходит в `completed`, в журнале фиксируется `status=partial`.
2. Сообщение не содержит стек-трейсов, SQL, внутренних путей, имён хостов, паролей, ключей и токенов (И-09; п. 4).
3. Разделение 403 и 404: объект вне области доступа возвращает 404, при этом в журнале фиксируется именно отказ в доступе.
4. При недоступности хранилища операция не подтверждается: транзакция откатывается целиком, частичных изменений нет, событие журнала не теряется.
5. Каждый отказ сопровождается записью журнала; `operation_id` в ответе позволяет проверяющему найти эту запись.
6. Один класс ошибки — один `code` во всех эндпоинтах; текст сообщения согласуется до реализации (вопрос 7.3).

### 5. Отметки времени и измерение норматива

Запись об отказе содержит `occurred_at` и `recorded_at`; отказы, зарегистрированные в окне замера норматива 5 минут, делают замер недействительным (условие штатной работы, P22-73, п. 5).

### 6. Зависимости и блокировки

P22-74 (аутентификация и права), P22-76 (журнал как приёмник отказов), P22-72 и P22-73 (операции-источники), P22-78 (диагностика и контроль состояния); вопрос реестра 7.3 — согласованные форматы и допустимые значения, без него перечень сообщений валидации не финализируется.

### 7. Определение готовности (DoD)

Кейсы TC-79-01…TC-79-08 пройдены; все классы ошибок воспроизведены на стенде с ожидаемыми `code`, сообщением и записью журнала; отсутствие секретов и трассировок в сообщениях подтверждено; результаты переданы в P22-81.
