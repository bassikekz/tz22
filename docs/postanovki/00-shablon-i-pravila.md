# Шаблон постановки и правила приёмки задач

Документ задаёт единую форму постановки задачи для исполнителя и обязательный
минимум проверок. Применяется ко всем задачам проекта P22; постановки лежат
в этом каталоге, по файлу на группу задач одной роли.

## 1. Форма постановки

| Раздел | Что содержит | Обязателен |
|---|---|---|
| Основание | документ и пункт ТЗ, из которого следует работа | да |
| Модуль и компонент | модуль M1…M16 и единица развёртывания по `docs/04-arhitektura-platformy.md` | да |
| Что реализовать | нумерованный перечень работ в терминах сущностей и операций | да |
| Данные | поля, типы, обязательность, правила заполнения, источник | для задач с хранением |
| Интерфейс | эндпоинты, назначение, требуемое право, коды ответов, включая отказ | для задач с API |
| Правила и инварианты | правила с номером пункта ТЗ, в том числе проверяемые на приёмке | да |
| Журналирование | какие операции и атрибуты пишутся в журнал и что в него не пишется | да |
| Зависимости и блокировки | задачи-предшественники и вопросы из `docs/05-otkrytye-voprosy.md` | да |
| Определение готовности | проверяемые пункты завершённости | да |
| Тест-кейсы | ID, тип, предусловие, шаги, ожидаемый результат, пункт ТЗ | да |
| Что не входит | явные границы объёма со ссылкой на пункт ТЗ или на другую задачу | да |

## 2. Правила формулирования

1. Каждое требование постановки прослеживается до пункта ТЗ. Требование без
   основания в ТЗ помечается «предложение Исполнителя» и подлежит согласованию.
2. Ожидаемый результат кейса описывает наблюдаемое состояние: ответ интерфейса
   или API, запись в базе, запись в журнале, видимость в интерфейсе.
   Формулировки «работает корректно», «данные отображаются правильно»
   недопустимы.
3. Значение, не заданное ТЗ (порог, веса, интервал, формат), не выдумывается:
   ставится ссылка на номер вопроса реестра открытых вопросов.
4. Бизнес-проверка не реализуется только на клиенте: каждому запрету интерфейса
   соответствует проверка на стороне приложения (п. 4 месячного ТЗ, раздел 10
   общего ТЗ).
5. Границы объёма указываются явно: что делается в другой задаче и что не входит
   в текущую итерацию (п. 5 месячного ТЗ).

## 3. Обязательный минимум негативных проверок

Этот перечень включается в постановку каждой задачи, которая затрагивает
соответствующую функцию. Пропуск любого пункта без обоснования — основание не
принимать работу.

| № | Проверка | Основание |
|---|---|---|
| Н-1 | Черновик материала не выдаётся участнику: ни в перечне, ни по прямой ссылке, ни через API | мес. ТЗ пп. 3.1, 3.2 |
| Н-2 | Неназначенный пользователь не получает назначение и не видит результаты других участников | мес. ТЗ п. 3.2 |
| Н-3 | Профиль чтения не изменяет данные и настройки: действия недоступны в интерфейсе и отклоняются сервером | мес. ТЗ п. 4 |
| Н-4 | Запрос без аутентификации отклоняется для всех прикладных операций | мес. ТЗ п. 4 |
| Н-5 | Прямой вызов API в обход интерфейса не обходит проверку полномочий | мес. ТЗ п. 4; раздел 10 |
| Н-6 | Пароли, ключи и токены отсутствуют в аудите и технических журналах (отрицательный поиск контрольного значения) | мес. ТЗ п. 4 |
| Н-7 | Значение введённого при имитации секрета не сохраняется ни в базе, ни в журналах, ни в отчётах, ни в интерфейсе | пп. 7.6, 7.7, 10.1 |
| Н-8 | Неполный результат не обозначается как успешный | мес. ТЗ п. 3.2 |
| Н-9 | Повторное выполнение операции не создаёт дублирующую запись (идемпотентность) | п. 9 (журналирование), мес. ТЗ п. 3.2 |
| Н-10 | Данные и результаты сохраняются после перезапуска и восстановления из копии | мес. ТЗ п. 4; проверка 5 п. 8 |
| Н-11 | Секреты отсутствуют в образах и репозитории | мес. ТЗ п. 4; раздел 11 |
| Н-12 | Кампания по инициативе AI-SecOps не запускается вне утверждённого сценария без подтверждения оператора | пп. 7.9, 8.1 |

Проверки Н-7 и Н-12 относятся к задачам этапа 2 общего объёма; в месячном объёме
CA_PS-2026-10 применимы Н-1…Н-6, Н-8…Н-11.

## 4. Определение готовности задачи разработки

Задача считается выполненной, когда одновременно:

1. реализован весь перечень раздела «Что реализовать», без переноса пунктов
   без письменного согласования;
2. изменения схемы данных оформлены миграцией, применяемой на чистом окружении;
3. проверки полномочий выполняются на стороне приложения;
4. операции и отказы в доступе фиксируются в журнале с обязательными атрибутами
   (пользователь, время, объект, операция, результат);
5. пройдены все кейсы постановки, включая применимые негативные из раздела 3;
6. сборка из переданного кода воспроизводима, секреты вне кода и образов;
7. в задаче YouTrack зафиксирован результат прогона кейсов и известные
   ограничения версии.
