# Способ развёртывания: монолит или микросервисы

Решение зафиксировано задачей [P22-102](https://bassikekz.youtrack.cloud/issue/P22-102)
и подлежит согласованию с Заказчиком в составе целевой архитектуры (P22-12) и отчёта
об обследовании (P22-15).

## Решение

**Модульный монолит ядра + выделенные сервисы для рассылки, публичного контура и коннекторов.**
Полная микросервисная декомпозиция по ~15 доменам ТЗ не выбирается.

## Обоснование от требований ТЗ

| Требование общего ТЗ | Что из него следует |
|---|---|
| 5: модульность, независимость основных компонентов, разделение процессов обучения, тестирования, атак, оценки и отчётности | обязательна модульность, но не обязательна сетевая изоляция модулей |
| 1.3, 15: платформа передаётся Заказчику для самостоятельного сопровождения и развития, без критической зависимости от Исполнителя | чем меньше развёртываемых единиц, тем ниже порог сопровождения силами Заказчика |
| 4.1: ~20 000 работников, территориально распределённая структура | нагрузка пользовательского контура умеренная; тяжёлый профиль только у массовых рассылок |
| 5, 13: масштабирование рассылки и обработки событий | отдельного горизонтального масштабирования требуют рассылка, трекинг и коннекторы каналов |
| 4, 5: контейнерная архитектура, распределённое развёртывание, безопасное обновление | Kubernetes, по одному чарту на компонент |
| 12: резервирование, RTO ≤ 4 ч, RPO ≤ 15 мин, доступность ≥ 99,9% | критичные компоненты в нескольких репликах, состояние — только во внешних хранилищах |
| 7.6, 7.7, 10.1: публичные учебные домены и landing pages, запрет хранения реальных секретов | публичный контур выносится в отдельный сервис с минимальными правами и без доступа к БД результатов |

Микросервисы на каждый домен дали бы распределённые транзакции между обучением,
кампаниями и risk scoring, собственный контур наблюдаемости и существенно более
высокий порог для передачи платформы на самостоятельное сопровождение — при
отсутствии требования масштабировать эти домены независимо.

## Состав развёртывания

**Ядро (один образ, модули с явными границами):**
учебные программы и материалы, обучение и тестирование, жизненный цикл кампаний,
оценка осведомлённости и устойчивости, рейтинги и baseline, группы риска,
исключения и спорные результаты, отчётность, RBAC, аудит, API панели управления.

**Выделенные сервисы:**

| Сервис | Назначение | Масштабирование |
|---|---|---|
| `campaign-worker` | отправка массовых рассылок, обработка событий доставки и переходов | горизонтальное, по длине очереди |
| `public-edge` | учебные landing pages, трекинг переходов, приём факта действия без сохранения значения секрета | горизонтальное, отдельный сетевой контур |
| `channel-connector` | коннекторы каналов: почта, мессенджеры, голос | по каналу, независимо |
| `integration-connector` | HR/AD, LMS, порталы, ITSM, report phishing, AI-SecOps, SIEM | по интеграции |
| `scheduler` | планирование запуска кампаний, периодического обучения и повторных проверок | одна активная реплика с блокировкой |

**Хранилища и шина:** PostgreSQL (прикладные данные), Redis (кэш, блокировки,
идемпотентность), Kafka либо RabbitMQ (события и очереди рассылки), OpenSearch
(журналы и аудит), объектное хранилище (учебные материалы и вложения),
Prometheus и Grafana (метрики).

**Развёртывание:** Kubernetes в контуре Заказчика; по одному Helm-чарту на компонент;
конфигурация и секреты — вне образов (Secret/внешний менеджер секретов); миграции
схемы — отдельным job; обновление компонентов без полной остановки платформы (раздел 12).

## Границы для месячного объёма CA_PS-2026-10

Октябрьский объём (публикация материала и назначение с учётом прохождения)
разворачивается как ядро + PostgreSQL на dev/test стенде: внешние каналы, рассылка
и интеграции в месячный сценарий не входят (п. 5 месячного ТЗ). Структура кода при
этом сразу закладывается модульной, чтобы выделенные сервисы подключались без
переработки ядра.
