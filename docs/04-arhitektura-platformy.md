# Архитектура платформы П.22: головной документ

Документ описывает целевую архитектуру платформы киберучений и проверки
устойчивости работников к методам социальной инженерии (CA PS) по всему объёму
общего ТЗ П.22 v.2 и фиксирует принятые архитектурные решения.

Приложения (детализация по областям):

| Приложение | Содержание | Ответственная роль |
|---|---|---|
| `arch/01-moduli-i-granicy.md` | карта модулей, границы, контракты, каталог событий, внешний API | Техлид — архитектор |
| `arch/02-domennaya-model.md` | сущности, состояния, инварианты, модель расчёта показателей | Senior-разработчик П.22 |
| `arch/03-integracii-i-kontrakty.md` | реестр интеграций, контракт с AI-SecOps, норматив 60 секунд | Middle-разработчик |
| `arch/04-bezopasnost-i-privacy.md` | модель ролей, защита результатов, запрет хранения секретов, аудит, SDL | Инженер ИБ |
| `arch/05-razvertyvanie-i-nadezhnost.md` | топология, масштабирование, отказоустойчивость, наблюдаемость | DevOps-инженер |
| `arch/06-ispytaniya-i-trassirovka.md` | уровни проверок, матрица трассировки, нормативы, чек-лист ввода | QA-инженер |

сопоставление требований с задачами YouTrack — `02-sopostavlenie-s-youtrack.md`.

## 2. Архитектурные принципы

| № | Принцип | Основание | Следствие для реализации |
|---|---|---|---|
| П1 | Модульность с явными границами: процессы обучения, тестирования, моделируемых атак, оценки и отчётности разделены | 5 | каждый модуль владеет своими данными; смежный модуль обращается только через контракт |
| П2 | Ядро — один развёртываемый модульный монолит; независимо масштабируются только рассылка, публичный контур и коннекторы | 5, 13, 1.3 | меньше развёртываемых единиц при сохранении масштабируемости нагруженных частей |
| П3 | Отсутствие критической зависимости от Исполнителя | 1.3, 4, 15, 24 | открытые компоненты с допустимыми лицензиями, воспроизводимая сборка из переданного кода, передача прав |
| П4 | Платформа не хранит реальные секреты работников | 7.6, 7.7, 10.1 | при имитации ввода фиксируется только факт действия; значение отбрасывается немедленно |
| П5 | Персональные и агрегированные результаты разделены по доступу | 7.13, 10, 10.2 | управленческая аналитика строится на агрегатах; персональные данные — по полномочиям |
| П6 | Действия участников и операторов фиксируются как события и попадают в аудит | 9 | единый формат события, журнал с контролем целостности |
| П7 | Контент и правила оценки версионируются, расчёты воспроизводимы | 7.2, 7.13, 7.19 | версия материала и версия правил указываются в результате |
| П8 | Автоматические воздействия выполняются только в рамках утверждённых правил | 7.9, 7.18, 8.1 | внеплановые и массовые кампании по инициативе AI-SecOps требуют утверждённого сценария либо подтверждения оператора |
| П9 | Конфигурация, секреты и данные отделены от приложения | 4 (мес. ТЗ), 5, 12 | перезапуск не теряет результатов; обновление без полной остановки |

## 4. Единицы развёртывания (сводно)

`core` (ядро с модулями M1–M4, M7–M12, M14, M16), `campaign-worker` (рассылка и
обработка событий), `public-edge` (учебные landing pages и трекинг),
`channel-connector` (почта, голос, мессенджеры), `integration-connector`
(внешние системы), `scheduler` (расписания), `web-admin` и `web-portal`
(интерфейсы). Хранилища: PostgreSQL, Redis, Kafka либо RabbitMQ, OpenSearch,
объектное хранилище; наблюдаемость — Prometheus и Grafana (6).

Топология, реплики, ресурсы, схемы резервирования и SLI — приложение
`arch/05-razvertyvanie-i-nadezhnost.md`.

## 5. Ключевые сквозные потоки

**П-1. Публикация материала и назначение обучения (объём CA_PS-2026-10).**
M1 сохраняет материал и реквизиты → оператор публикует версию (право ограничено,
M11) → событие публикации → M2 создаёт назначение тестовой группе → участник
видит назначение в `web-portal` (черновик не выдаётся) → подтверждение
прохождения фиксируется с материалом, версией, участником и временем → M12
журналирует все операции. Норматив: назначение доступно не позднее 5 минут после
публикации (7.3; задачи P22-73, P22-81).

**П-2. Фишинговая кампания.** M4 формирует кампанию (цель, аудитория, период,
сценарий, канал, допустимые действия, сложность, exclusion list, контрольная
группа, ответственный) → согласование и утверждение (7.16) → `scheduler`
планирует запуск с рандомизацией времени отправки (7.5) → `campaign-worker` через
`channel-connector` выполняет рассылку → `public-edge` принимает переходы, факт
попытки ввода (без сохранения значения) и открытие безопасного вложения → M6
нормализует события, учитывает сообщение работника о фишинге и считает
time-to-report → M7 обновляет показатели, M8 — группы риска, M12 — журнал.

**П-3. Голосовая и messenger-проверка.** M4 даёт утверждённый сценарий и
согласованные категории работников → `channel-connector` проводит взаимодействие
по согласованным каналам и контролируемым отправителям → M6 фиксирует результат
без чувствительных данных → M7 и M8 учитывают результат (7.7, 7.8).

**П-4. Адаптивное обучение.** M6 фиксирует тип ошибки → M8 по утверждённым
правилам назначает учебный материал, короткий корректирующий курс, повторное
тестирование или повторную проверку → M2 и M3 исполняют назначение → M7 оценивает
изменение результата после обучения (7.18).

**П-5. Обмен с AI-SecOps.** M12 и M7 формируют исходящие сведения (результаты,
показатели, рейтинги, группы риска, журналы аудита, события безопасности) →
`integration-connector` передаёт их, критичный результат — не позднее 60 секунд
(9) → входящие рекомендации принимаются как предложения: автоматическое
назначение обучения допускается только по утверждённым правилам, запуск массовых
и целевых кампаний — по утверждённому сценарию либо после подтверждения оператора,
все действия журналируются (8.1).

**П-6. Пересмотр спорного результата.** Обращение работника (напрямую либо из
системы обработки обращений) → M9 регистрирует возражение → ответственный
изменяет статус результата с фиксацией основания → результат исключается из risk
scoring → M7 пересчитывает показатели, M8 обновляет группы риска, история
пересмотра и действия ответственных журналируются (7.20).

## 6. Реестр архитектурных решений

| № | Решение | Основание | Последствия | Отклонённая альтернатива |
|---|---|---|---|---|
| AD-01 | Ядро — модульный монолит, отдельно масштабируются рассылка, публичный контур и коннекторы | 5, 13, 1.3, 15 | меньше операционной сложности при передаче Заказчику; модульные границы соблюдаются на уровне кода | микросервисы на каждый домен: распределённые транзакции между обучением, кампаниями и scoring, высокий порог сопровождения |
| AD-02 | Публичный контур `public-edge` вынесен отдельным сервисом без доступа к базе результатов | 7.6, 10, 10.1 | компрометация публичного контура не даёт доступа к персональным результатам | публикация ядра наружу |
| AD-03 | События участников и интеграций передаются через шину (Kafka либо RabbitMQ) | 7.6, 9, 13 | пиковые события трекинга не теряются, обработка масштабируется | синхронная запись событий в ядро |
| AD-04 | Журналы аудита хранятся в отдельном хранилище с контролем целостности и разграничением доступа | 9, 10 | выполняются требования поиска, экспорта и защиты журналов от изменения | хранение журналов только в основной БД |
| AD-05 | Версионируются материалы, тесты и правила оценки; результат ссылается на версии | 7.2, 7.13, 7.19 | расчёты воспроизводимы, история сопоставима | расчёт только по текущим правилам |
| AD-06 | Единый справочник персонала и оргструктуры — источник для аудиторий, исключений и агрегатов | 4.1, 8, 7.17 | целевые группы и рейтинги строятся на одних данных | формирование аудиторий в каждом модуле отдельно |
| AD-07 | Воздействия AI-SecOps исполняются только по утверждённым правилам либо после подтверждения оператора | 7.9, 8.1 | исключён несогласованный запуск массовых и целевых кампаний | прямое исполнение входящих команд |
| AD-08 | Конфигурация и секреты хранятся вне кода и образов | 4 (мес. ТЗ), 10 | образы переносимы между средами; секреты не попадают в поставку | конфигурация внутри образа |
| AD-09 | Значение введённого секрета не сохраняется ни в одном узле обработки | 7.6, 7.7, 10.1, 19 | требует контроля логов веб-сервера, буферов и трейсов | хранение в обезличенном виде «на время разбора» |
| AD-10 | Развёртывание в Kubernetes, по одному чарту на компонент, миграции схемы отдельным job | 4, 5, 12 | обновление компонентов без полной остановки | единый монолитный манифест |
| AD-11 | Рассылки, трекинг и landing pages берутся из готового открытого компонента (GoPhish), обучение и тестирование — из открытой LMS; собственная разработка — связующий слой: доступ, аудит, оценка и показатели, группы риска, пересмотр результатов, отчётность и панель, интеграции, планировщик | 6, 1.3, 15, 24 | объём собственной разработки сокращается на подсистемы рассылки, курсов и тестов, что делает шестимесячный срок выполнимым командой из трёх человек; взамен появляется ответственность за конфигурацию, обновление и лицензионную чистоту внешних компонентов, а модули M5, M6 и часть M1–M3 становятся адаптерами к ним | собственная реализация рассылок, трекинга, курсов и тестов: 60–100 человеко-дней дополнительно, в срок не укладывается |

## 9. Ограничения месячного объёма в целевой архитектуре

Объём CA_PS-2026-10 реализует часть M1, M2, M11 и M12 и разворачивается как
`core` с PostgreSQL на dev/test стенде: каналы, рассылка, интеграции и публичный
контур в месячный сценарий не входят (месячное ТЗ, п. 5). Структура кода сразу
закладывается модульной, поэтому выделение `campaign-worker`, `public-edge`,
`channel-connector` и `integration-connector` на последующих итерациях не требует
переработки ядра. Приёмка месячной части не подтверждает требования разделов 8,
12, 13, 18 и 19 общего ТЗ.
